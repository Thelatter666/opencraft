# 05 · 开发流程：项目经理-开发者模式

## 1. 模式定义

本项目采用 **PM-开发者多对话协作模式**：用户是唯一转发者；"项目经理（PM）"对话负责规划/审查/发任务；若干"开发者"对话各自**无共享会话记忆**，只凭收到的自包含任务提示词工作。

角色与职责：

| 角色 | 职责 | 禁止 |
|---|---|---|
| 用户（转发者） | 在对话间搬运提示词与结果 | 替 PM 或开发者做技术决策 |
| PM 对话 | 路线图、任务拆分、接口契约、验收、状态簿记 | 直接写实现代码 |
| 开发者对话 | 在边界内实现、自测、报告 | 越界改文件、重构无关代码 |
| **美术总监对话**（2026-09-18 设立） | 美术资产（贴图/模型/图标）的规格制定与制作；`assets/` 内产出 | **写 C++ 代码**（含"用代码生成贴图"）；改 `docs/` 规格；写 `STATE.md`/记忆层 |

核心价值：每次任务都"冷启动"，因此**自包含任务卡**与**落盘的项目状态**是整个模式的承重墙。

## 2. 标准提示词（定稿）

### PM 对话底座
```markdown
你是这个项目的"项目经理 + 架构师"。
目标：用 C++ 开发一个类 Minecraft 的完整游戏，在公开可观察的玩法、机制、手感上尽量对齐
Minecraft Java Edition。必须使用原创代码与合规资产，不复制 Minecraft 的代码、纹理、音效、名称、商标。
项目通过多个"无共享记忆"的开发者对话协作，用户是唯一转发者。你负责规划路线图、架构、任务、
接口和验收标准；每次给用户一段可直接转发给某个开发者的自包含提示词；用户贴回开发者结果后，
你负责审查、更新状态、决定下一步。
尽量把实现自由留给开发者，你只规定目标、边界、接口、验收和文件冲突范围。优先可编译、可运行、可测试。
一次不要铺太大。每轮输出：当前状态、关键决策、下一步任务、要转发的开发者提示词。
必读文档：opencraft/README.md 及 docs/00–06；数值以 docs/research/ 为准。
```

### 开发者对话底座

**★ 首句必须是「你是「卡编号」的开发者」**（用户 2026-09-16 要求）：zcode 按用户发出的

> 调研卡/审查卡同理，首句写「你是「T-R1-流体调研」的研究员」之类，让角色也进对话名。

### 美术总监对话底座（2026-09-18 设立）

职责切分（用户 2026-09-18 明确）：**代码开发由开发者进行，美术资产由美术总监制作。**
美术资产 = 方块/物品贴图（16×16 PNG）、生物模型（`.vox`）、图标、色板。**不含**字体（见 §2.1）。

```markdown
你是「<ID>-<slug>」的美术总监。
你没有其他对话记忆，只能根据收到的任务提示工作。项目：C++ 类 Minecraft 沙盒游戏
OpenCraft，原创代码与合规资产——风格可对齐"16×16 像素风"这个风格类别，但不得接近
具体原版纹理的构图与配色。
你负责美术资产（贴图/模型/图标）的规格与制作，产出落在 assets/ 下。
★ 你不写 C++ 代码，包括不得用代码程序化生成贴图——那是我们要拆掉的耦合。
完成后输出：产出清单（含路径）、规格说明、CREDITS 条目草稿、已知问题、给项目经理的备注。

任务卡：/Users/happy/Desktop/opencraft/docs/tasks/<ID>.md
```

### 美术资产三条硬规则（AI 生成相关，2026-09-18 立）

1. **AI 输入禁止含 MC 资产**：不得把原版贴图/截图/官方美术喂给模型做"参考重绘"
   （`docs/04` 红线 2：改色/翻转/重采样也算衍生）。要参考只喂**文字描述**。
2. **提示词不得点名 MC**：不得出现 "Minecraft-style" 之类。这是红线 5（观感不逐项对齐）的执行手段。
3. **证据链照旧**：`assets/CREDITS.md` 每条须写 `工具 + 提示词摘要 + 日期 + 人工后处理`。
   AI 生成不豁免留痕——因为它更易产出接近原版的东西，更该留痕。

> ⚠ **非法律意见**：AI 生成物的著作权归属各国未定论（美国现行立场倾向纯 AI 生成物不受版权保护）。
> 本项目不靠著作权维权、靠不侵权，故风险可控；若将来单独授权美术资产，须先咨询律师。

### 任务卡模板（PM 每次发出的开发者提示词必须完整包含）
```markdown
# 任务 <ID>：<标题>
里程碑：<M?>  前置任务：<IDs 或"无">
## 目标（一段话说清做完什么）
## 允许触碰的文件/目录（白名单，含明确禁碰项）
## 接口契约（新增/依赖的 API、文件格式、数据结构签名，冻结项标明）
## 数值/规格依据（指向 docs/0X-*.md 的具体章节）
## 验收标准（可执行：命令 + 预期结果；含构建必须通过、现有测试不回归）
## 已知风险与提示（来自 PM 审查或上一任务备注）
```

### 卡面归档（`docs/tasks/`，自 T010 起生效）

卡面是接口契约的载体，必须落仓库，否则复核者只能依赖 PM 转述。**卡面在派发前落
`docs/tasks/Txxx.md` 并提交，转发文本与之一致**；已派发卡的索引与来源等级见
[`docs/tasks/README.md`](tasks/README.md)。

规则：

1. **先落盘再转发**：卡面文件先写入并提交，再输出给用户转发，二者内容一致（消除转录差）。
   ★ **转发形态（用户 2026-09-15 明确要求）**：PM 每轮**只输出「开发者对话底座 + 卡面的
   完整绝对路径」**，**不再把卡面正文贴进对话**。卡面已落仓库且自包含，开发者直接读文件
   即可——贴全文只会让用户多搬一次，且容易在转录中失真。例：

   ```markdown
   你是这个项目的开发者。
   你没有其他对话记忆，只能根据收到的任务提示工作。项目：C++ 类 Minecraft 沙盒游戏，原创代码与合规资产。
   先理解任务目标、边界、接口和验收标准。能合理假设就写明假设继续；不能就提出最少澄清。
   只改允许范围内的文件，保持可编译、可测试。
   完成后输出：变更摘要、文件列表、构建/运行/测试方法、结果、已知问题、接口变更、给项目经理的备注。
   实现方式自行决定，优先简单可靠。开工前先读取任务卡中列出的规格文档章节。

   任务卡：/Users/happy/Desktop/opencraft/docs/tasks/T-D14.md
   ```

   前提：卡面必须**自包含**（目标/白名单/接口契约/规格依据/验收标准齐全），
   且路径一律完整绝对路径（规则 5）。
2. **卡面不写状态**，只写"要做什么、怎么算过"；状态唯一权威仍是 `STATE.md`。
3. **卡面是派发时点快照，不得改正文**；一切修订追加「变更记录」（日期、内容、依据、授权）。
4. **★ 对话中的报告一律用「简短版」**（用户 2026-09-16 明确要求，**取代**旧的
   "报告不一律归档"）：
   - 报告正文**落盘** `docs/tasks/Txxx.report.md`（含调研卡、审查卡），PM 读文件验收。
   - **对话里只输出简短版 + 完整报告的绝对路径**，用 **txt 代码块**包裹（不是 markdown），
     便于用户原样转发。
   - 简短版建议形态：状态 / 交付（含路径）/ 核心结论 / **需 PM 裁决项** / 已知问题。
   - 卡片（`docs/tasks/Txxx.md`）里的验收标准须同步写明本条，开发者才会照做。
   - **白名单须显式列出证据目录 `docs/qa/T<ID>-<date>/`**（与报告文件并列）——
     自 T009 起 `docs/qa/` 就是既有惯例，不是例外；漏列会让实机截图无处归档
     （T-M1 因此把截图留在 `/tmp`，复核需另取件）。
5. **路径一律写完整绝对路径**（如 `/Users/happy/Desktop/opencraft`），不用家目录简写 `~`：
   文档可能被其他工作区或另一台机器上的会话读取，简写会变成悬空指针。
   （例外：`docs/tasks/` 中作为逐字快照归档的卡面正文，即使含 `~` 也保持原样。）

   > **★ 白名单自洽检查（T-D45 教训，2026-09-18）**：若白名单开了某个源码目录
   > （如 `game/client/src/**`），**必须同时把该目录的构建登记文件列进去**
   > （`game/client/CMakeLists.txt`）——否则开发者新增 `.cpp` 时无处登记，
   > 只能被迫写成 header-only 或越界改文件。T-D45 卡面列了 `tests/CMakeLists.txt`
   > 却漏了对等的源码目录 CMakeLists，**属 PM 疏漏**；开发者发现后未自行越界、
   > 上报待裁决，处置正确。⇒ 检查项：**列了一边的 CMakeLists 就必须列另一边。**
   >
   > **★ 过程垃圾不得入仓（T-A3 教训，2026-09-18）**：验收工具/脚本产物
   > （`__pycache__/`、`*.pyc`、临时 PSD、中间稿）**不得随证据目录提交**。
   > T-A3 提交了 `__pycache__/art_source.cpython-312.pyc`（18 KB 二进制），
   > PM 已清除，并顺带清掉 T-A1 的历史遗留同类垃圾。
   > ⇒ 检查项：**证据目录只收最终产物（截图/日志/复跑脚本源码），不收运行产物。**

## 3. 工作循环

```
PM：拆任务卡 ──► 用户转发 ──► 开发者：实现+自测 ──► 结果回贴
 ▲                                                        │
 └── 审查（验收标准逐条核对）→ 更新状态 → 下一张任务卡 ◄────┘
```

审查规则：
1. 验收标准逐条核对，"大概能用"不算过；构建失败/测试回归一律打回。
2. 接口变更必须由 PM 记录进规格文档后才能被后续任务依赖。
3. 每个里程碑结束做一次整仓构建+全量测试+手感清单人工验收（`01-gameplay-spec.md` §8）。
4. 任务粒度：单个开发者对话一次可完成；超过就拆。（实测约 1 小时/卡，见 §3.3。）

> **★ 排卡排序依据：结构优先，不看"玩家是否可见"**（用户 2026-09-16 明确纠正）。
> PM 一度把"该来点可见进展了"当作排序理由插到结构卡前面，这是**PM 自身的焦虑，
> 不是用户的需求**。用户的原话是「在合适的时候让我看见进展就行，没必要把这件事
> 的重要性放大。开发重心保持结构优先」。
>
> 因此：排卡只看**结构依赖与风险**（什么最贵、什么最该先做、什么会阻碍后面最多），
> **不**因为"连续几张卡玩家看不见"而插入内容卡。可见进展是结构的副产品，不是目标。

> **★ 凡判定"与原版不一致"（即缺陷），必须先取得原版基准**（2026-09-17 立，血泪教训）。
> 基准来源按可信度排序：
> - **(a) 原版实机读数**（bot/`mineflayer` 接入真实世界逐格读方块）—— 最强
> - (b) 可复核的公开来源（wiki **正文** + 规范 URL + 访问日期）
> - (c) 用户观感 —— **只能用于提出怀疑，不能用于定性**
>
> **没有 (a) 或 (b) 时，一律定性为"待校准"，不得定性为"缺陷"。**
>
> 反例（T-F1.ruling2，已由 ruling3 推翻）：用户说"水只朝一个方向流、不像 MC"，
> PM 探针只证明了"OpenCraft 现在是 X"，**从未证明"原版不是 X"**，就定性成缺陷并
> 限制了对外表述。后经机器人接入原版 1.19.2 实测：
> **原版就是硬门控**（其余三向 = 0 水），OpenCraft 行为与原版一致，不是缺陷。
>
> 三个具体失效点，逐条防：
> 1. **别把观感升级为判据**——观感只能用来提出怀疑；
> 2. **别在同一来源里挑更符合预期的那句**——wiki 配图写 prioritize（优先）、
>    正文写 lowest flow weight（排他），PM 挑了前者，结果原版是后者；
>    同一来源内部冲突时，**两个都记下来，去要 (a)**；
> 3. **定性"缺陷"必须有对照组**——知道"正确的应该是什么"才能说"这个不对"。

### 3.3 开发节奏实测（2026-09-16 修正，取代"1–3 天"的旧假设）

旧文本里的「单个任务约 1–3 天人的工作量」是**人类工时假设，不是本项目实测**，
用它排期会**高估约一个数量级**。实测（git 时间戳）：

- **M1 全程（T001→T009）≈ 8.7 小时**，中位 **≈ 50 分钟/卡**
  （T001 37min / T002 30 / T003 55 / T004 48 / T005 72 / T006 56 / T007 33 / T008 50 / T009 85）
- M1 后手感卡同量级：T-D7 26min、T-D13 16min、T-D14 67min（含实机取证）

⇒ **真实吞吐约 1 小时/卡。** 瓶颈不在开发速度，而在**转发往返 + PM 验收**
  （干净检出 configure ≈90 s + build ≈100 s，加上读码与核数值）。

排期时按此估算；卡切得够小仍是前提。跨层大卡（如 T-F1 跨 voxel/render/client）
实测也能在一轮内交付，**不必因"怕做不完"而过度拆分**。

### 3.2 纯重构卡的验收装置（自 T-M1 起，2026-09-16 固化）

「零行为变化」不能靠"看着没变"。纯重构卡一律用**三层证据**自证（T-M1 首创并验证有效）：

1. **冻结项逐字节**：GLSL 原始串、字体/数据表、⚖ 常量值 —— 按序逐字节比对。
   推荐做法：扫**数值字面量多重集**，判据是「**任何已有字面量不得消失**」
   （改值必然导致旧字面量消失，这条比逐行 diff 更抗干扰）。
2. **逐块 token 等价**：搬出的代码块与基线逐 token 相同（**含注释**）。
3. **实机 A/B 决策日志 diff**：同一套注入脚本分别跑拆分前后的两个二进制，
   决策日志（挖/放/倒水/存盘的日志行）**逐字节一致**；截图比对时注明"像素完全相同/若干张"。

配套要求：
- **小步提交**：每拆一块一提交，便于二分定位，PM 也好看 diff。禁止一个大提交整体打散。
- **存量测试数不变**：纯重构卡一律写"存量测试数不变"，
  **不得**同时开"可补单测"的口子（T-M1 卡面曾自相矛盾：267 不多不少 vs 可补单测）。
  ⚠ **PM 已复发两次**（T-M1、T-D40），两次都是开发者按更严一侧执行并指出。
  ⇒ **写卡面模板时的硬检查项**：若卡面出现"存量 N 全绿 / 一条不多一条少"，
  则白名单里**不得**再出现 `tests/**（可补单测）`。二者只能有一个。
- **发现 bug 不顺手修**：写进报告建议表。混进重构会让"零行为变化"失效，
  出事分不清是重构引入还是修 bug 引入。
- **卡面行号锚点必须现数**：给 `file:line` 前先 `wc -l`（T-M1 卡面沿用旧统计 1628，
  基线实为 1740，已复发一次）。

### 3.1 GUI 实机取证手法（硬规则，自 2026-09-15 生效）

GUI 类验收（按键注入、菜单点击、"实机是否真的触发"）一律遵守以下三条：

1. **键盘注入必须走 HID 层**：`CGEventCreateKeyboardEvent` +
   `CGEventPost(kCGHIDEventTap)`，脉冲 **86–87 ms**。
   **禁用 `osascript key code`**——它的脉冲只有 2–5 ms，短于客户端每帧轮询周期（≈11 ms），
   必丢。历史上"功能失效"的假结论全部由此而来。
2. **HID 注入在本机不稳定**（T-D14 实测，债务 T-D21）：
   - 注入通道**会话相关地**时灵时不灵；
   - 生效时 **GLFW 会在窗口失去 key 焦点时清除按键状态**，实测约 **9 tick 后**按键即被清掉，
     故"按住 W 走很远"在本机做不到。
   ⇒ **取证手法**：把决定性场景放在注入生效窗口内（例如把测试墙贴近出生点），
   或改用改写存档/直接定位的方式。产品代码**不得**为此做任何妥协。
3. **窗口号按 PID 反查**（按名匹配会命中死窗口）；激活 + 注入 + 截图须在**同一进程**内完成；
   **`Ctrl+Space` 被 macOS 吞掉**（输入法切换快捷键）——故"按住 Ctrl 疾跑 + 空格跳"的
   合成验证**必然失败**，改用**双击 W** 进疾跑后再跳。这是系统快捷键，不是引擎缺陷。
4. **`CGWindowListCreateImage` 在 macOS 15 SDK 已 obsoleted**（编译直接报 unavailable）。
   窗口截图仍用 `screencapture -x -o -l<windowID>`；若在进程内调用该 API，
   须退化为起子进程跑 `screencapture`（仅影响验收工具链，不影响产品代码）。
5. **★ 渲染类缺陷单测覆盖不到，必须靠实机**（T-E1 确立）。
   实例：掉落物的渲染模型矩阵写错（`T(-0.5)` 应为 `T(-0.5 × 边长)`），
   立方体被压到地面以下 ⇒ 画面里看不见；但"实体存在/物理正确/拾取正确"**全部正常**、
   单测全绿。同类还有 T-I2 的求值顺序崩溃。
   ⇒ **凡涉及渲染/求值顺序的改动，验收必须含实机证据，不能只看单测。**
6. **"画面里到底有没有这个东西"的判据**：相机静止时**连续两帧逐像素完全相同**
   ⇒ 说明没有任何东西在动（如掉落物的自转/浮动）。T-E1 用它定位到渲染缺陷，
   这个判据便宜且有效，推荐复用。
7. **★ HID 脉冲宽度与"抬起沿"（T-D40 实测，2026-09-17）**：
   - **60 ms 脉冲对 W 完全无效**，**15 ms 密集脉冲反而生效** —— 与"脉冲越长越稳"的直觉相反。
   - **双击类操作必须真的发 up**：密集脉冲不产生"抬起"沿，客户端
     `in.forward_press = w && !prev_w` **收不到边沿** ⇒ 疾跑双击永远不会触发。
   - 实证：走/跳/挖/放 可用密集脉冲复现；**疾跑双击**必须发完整的 down→up→down。
8. **★ 合成鼠标移动本机严重非线性**（T-M2 实测）：**30 px 的移动量就能打到 89° 钳位**
   ⇒ 用"注入鼠标移动"来瞄准极不可靠。**改用潜行的水平视线**来设定朝向。
9. **HUD 第 N 格 = 槽 N−1**（1-based 显示 vs 0-based 存储，易差一）。
10. **`screencapture` 对非前台窗口返回旧表面**（不是当前画面）⇒ 截图前必须先激活目标窗口，
    否则会用一张过期图像得出错误结论。
11. **显示缩放**：本机为 **1x**（无 Retina backing scale）。任何 HiDPI 相关修复在本机
   **无法实证**，须在报告中显式标注"未经 Retina 验证"，并由 PM 登记为待验债务，
   不得当作已修复对外声称（见债务 T-D19）。
12. **★ 美术卡的生效判据（T-A4 确立，2026-09-18）**：美术类改动**不能只看"画面变了"**。
   三条缺一不可：
   - **① 启动日志的加载计数**（如 `atlas: N/63 block tiles loaded`）——
     因为**文件名写错是静默回退**，画面上表现为"没生效"，而日志会告诉你真相；
   - **② 同机位逐像素差异**——证明画面确实变了；
   - **③ 一个"应当没变"的对照组**（如一个未改动的方块，实测 0.0% 变化）——
     **证明差异只来自目标资产，而不是别的资产也变了或被误读**。

   ⚠ 只有 ② 没有 ③，无法排除"别的贴图也变了"；只有 ① 没有 ②③，
   只证明"文件被读进去了"，**不证明"上屏的是它"**。
   ⇒ 首批/第二批方块贴图（T-A3/T-A4）均按此三条取证，后续美术卡沿用。
13. **★「资产已落盘」≠「玩家能看见」（T-A4 教训，2026-09-18）**：美术卡凡制作
   **世界里不自然生成的方块**（如 `cobblestone`/`sandstone`）的贴图，
   须先确认其**获得途径**存在（worldgen / 启动包 / 掉落表 / 合成）。
   否则资产合格但**游戏内不可达**——T-A4 的 `rubble_rock`/`grit_slab` 即此例
   （全仓只在 `item_registry.cpp` 注册，无任何获得途径，登记为 T-D53）。
14. **★ 截图 A/B 前先确认装置状态，并把"画面静止"当门而不是事后判据**
   （T-B1 PM 侧装置实测，2026-09-18；rev2 增补见"流式平台门"）：
   - **注入失败会伪装成渲染回归**：ESC 没送达时画面明亮且在动，与"渲染变了"在像素上
     不可区分（实测差 **920,288 / 957,440** 像素，全是假象）。
     ⇒ 取证脚本必须有一条**机器可读的状态判据**（如日志里的 `EVIDENCE paused=`），
     **轮询到它才拍**，否则整轮证据作废。
   - **流式平台门（暂停帧的另一半）**：暂停**会把流式进度一起冻住**——ESC 早落一次晚落一次，
     两次运行就停在**不同的世界**上，而各自内部"连拍相同"照样成立（实测假差异
     **566,858 / 957,440**，差点把通过的说成失败）。⇒ 暂停**之前**等 `fps` 行的
     `chunks/stream-meshed` 读数**连续三行相同**；"两连拍 md5 相同"只是门②，不是门①。
   - **暂停帧 ≠ 静止帧**：暂停后画面仍可能未定型 ⇒ 连拍两张（间隔 ~0.4 s）**md5 相同**
     才算定型（`§3.1` 第 6 条），并把这条从"判据"升级为"门"：不满足就等、不拍。
   - **"两次运行本来就不一样"的东西要钉死再比**：随机初始朝向、自然刷怪、粒子
     （壁钟驱动）都会让**同一个二进制**两次运行产生差异（实测 452 / 11,607 像素）。
     ⇒ A/B 前把噪声源做进夹具（本案：固定 yaw + 关自然刷怪），
     并**先量出噪声地板**（本案实测 = 0 像素），再报"两棵树相同"。
   - **两套现成装置，别重新发明**：静态定格 A/B 用
     `docs/qa/T-B1-2026-09-18/pm_verify/run_scene.sh`（四道门脚本 + 三则夹具补丁，
     暂停态召唤，噪声地板已量=0）；**要观察运动中的行为**用
     `docs/qa/T-B1-2026-09-18/tools/run_evidence.sh` + `apply_evidence_patch.py`
     （每 tick 钉住生物、可走路可受击）。B2/B3/B4 每只模型都直接复用其一。
   - ★ **夹具自身的约定也要被验证**（同条的镜像教训，2026-09-18）：PM 的 y-up 夹具
     被正确解析却渲染成贴地平板，一度被误读成"模型画飞了"——**"探针说有问题，先疑探针"**。
     `.vox` 是 **Z-up**；调色板 PNG 格号=颜色索引号；这两个约定同时写给 B2 卡面与夹具作者。
   - ★ **B2b 追加：暂停帧装置的取景几何账与三条死路**（数字见
     `docs/qa/T-B2-2026-09-18/pm_verify/README.md` §3/§4）：暂停菜单带固定在屏幕中部
     （底缘 y≈410/748）、热栏顶缘 y≈690、眼高 1.62 ⇒ 召唤距离要按生物身高选
     （**1.4 格高用 d=4.5**，全身恰好落在两死区之间；d=5 差 1 px 被截头顶）；
     **横移生成点不可用**（落点地形不受控，实测埋进草阶只剩耳朵 127 px）；
     **暂停态注入鼠标俯仰无效**（鼠标未捕获，逐帧与不注入相同）——**修法：俯仰要在按 ESC 之前做**。
     人形（B3）实高 **1.8 格**（`mob_type.cpp:107` 现数）> 眼高 1.62 ⇒ 头顶投影在地平线上方、
     **任何距离都落在菜单带内** ⇒ B3 取证要么"先俯仰后暂停"，要么接受菜单盖头顶、只取身体逐像素判据。

15. **★ "扩区间类改动"的存量断言零翻转是预期行为，不是安全信号**（T-B2b 实证，2026-09-18）：
   把契约区间从 1..8 扩到 1..16 时，**存量断言一条都不翻转**（v1/v2 下 9 都归躯干、10..16
   无人断言）——风险是**全绿掩盖语义漂移**。⇒ 这类卡的区分度**必须**由新用例把边界钉死
   （T-B2b 钉 8/9/10/16/17/255 五点 + 全区间穷举），或加一组**同夹具两二进制对照**
   （T-B2b 的眼睛演示：v2=4 joints vs v1=3 joints）。**"改完全绿"本身不算证据。**

## 4. agentmemory 协作协议（已实测）

经实测，agentmemory MCP 在本环境可用，作为 PM-开发者模式的外置共享记忆层：

### 已验证可用 ✅
| 能力 | 用途 | 用法 |
|---|---|---|
| `memory_action_*`（任务板） | 任务=action，`requires` 字段表达依赖 | PM 建 M1–M6 任务卡并连依赖；开发者完成后 `memory_action_update` 置 done |
| `memory_lease`（租约） | 防止两个开发者对话同时改同一区域 | 开发者开工前对任务 action `acquire` 租约（TTL 10 分钟，可续）；PM 发现冲突先查租约 |
| `memory_lesson_*`（教训） | 跨对话沉淀构建坑/接口约定 | 每次审查后 PM 存 lesson（含 confidence）；开发者开工前 `memory_lesson_recall "opencraft <模块>"` |
| `memory_save` / `memory_recall`（语义记忆） | 架构决策、接口契约的长期记忆 | PM 每个关键决策 `memory_save type=architecture project=opencraft`；冷启动开发者用 `memory_recall` 恢复上下文 |
| `memory_facet_tag`（标签查询） | 按优先级/领域捞任务 | 如 `dimension:priority AND value:urgent` |
| `memory_snapshot_create` | 里程碑快照 | 每 M 结束时建快照，可回滚记忆状态 |
| `memory_crystallize` / `memory_reflect` | 里程碑复盘 | 把完成的 action 链结晶为摘要，供 PM 写复盘 |

### 已验证不可用 ❌
- `memory_slot_*`（固定槽位）：后端持续 500。PM 状态改用"根目录 STATE.md + memory_save 冗余"双写，见 §5。
- 信号/哨兵/网格同步：适合同进程多代理，本项目开发者对话靠用户转发，不使用。

### 冷启动协议（每个开发者对话开工前执行）
```
1. memory_recall  "opencraft <任务领域>"     ← 恢复相关决策/背景
2. memory_lesson_recall "opencraft <模块>"   ← 避免已知坑
3. 读任务卡列出的规格文档章节（任务卡自带路径）
```
若运行环境没有 agentmemory MCP，则退化为只读规格文档——因此**任务卡必须自包含**，记忆只是加速器不是依赖项。

## 5. 状态与记忆的权威位（P-001 协议，2026-09-14 定）

曾经的做法是"STATE.md（权威）+ memory_save（冗余）双写"。**该协议已作废**：实践发现双写的记忆
半边只会漂移（项目状态在四处各存一份、出现三种互相矛盾的内容，详见 P-001 审计）。

现行协议——**每类信息只有一个权威位**：

| 信息类别 | 唯一权威位 | 写入者 |
|---|---|---|
| 进度/任务表/决策/债务（会变） | `opencraft/STATE.md` | **仅 PM** |
| 接口契约/规格/流程规则 | `docs/`（含本文件、`docs/tasks/`） | **仅 PM** |
| 任务板/依赖/认领 | agentmemory `memory_action_*` | PM 建卡，开发者置 done |
| 方法论/环境坑/教训（很少变） | agentmemory `memory_lesson_*` + PM 记忆文件 | PM（开发者可读不可写） |
| 代码真相 | git 历史 | 开发者提交，PM 审查 |

规则：
- **绝不把进度写进记忆层**（内置记忆或 agentmemory 的 memory/lesson 都算）——记忆层只放
  「指针 + 方法论 + 无法从仓库推出的裁决」。
- **开发者不写 STATE.md、不写 `docs/` 规格、不写记忆文件**；只写自己的分支与卡面指定的报告文件。
  **调研卡同样适用**：调研/审查得出的规格建议、状态变更、债务登记，一律以**建议表**形式写进
  报告交 PM 落盘，**不得自行改文件**（2026-09-15：research/07 卡直接改了 STATE.md 与
  `docs/03 §6`；内容虽被 PM 追认，但流程违规，此后卡面须显式写明此条）。
- 收口轮写入顺序固定：先落 STATE.md（事实）→ 再写记忆/lesson（方法论）→ 最后核对 `MEMORY.md` 索引。
- 每次收口做三方对账：git ⇄ STATE.md ⇄ agentmemory actions，不一致**以 git 为准**。

## 6. 分支与提交纪律

- 仓库单 `main` 分支 + 任务短分支（`task/<ID>-<slug>`），验收通过后合入；禁止未验收合入。
- 提交信息格式 `task<ID>: 摘要`；每个任务至少一个提交，保证可回滚。
- `assets/` 单独提交并在提交说明注明来源许可（CC0 来源/自制）。

### 并行任务必须独立 worktree（硬规则）

多个开发者对话**不得共用同一个工作目录**——曾发生并行任务互相切分支、未提交改动混入他人
分支堆的事故（T004/T005/T006 实测）。开工第一条命令：

```bash
git worktree add /Users/happy/Desktop/opencraft_worktree/opencraft-<task> task/T<ID>-<slug>
```

- **worktree 根目录固定为 `/Users/happy/Desktop/opencraft_worktree/`**（不要建在仓库旁或 `/tmp`，
  避免污染桌面与临时目录被清）。
- 全部工作（构建/测试/提交）只在 worktree 内进行；**主工作区 `opencraft/` 只归 PM 做验收合并与簿记**。
- PM 验收合并前，先在干净环境以 merge commit 复验，再动主树。
- 任务验收后由 PM 清理：`git worktree remove <dir>`（只删工作目录，**分支与历史保留**）。
- 卡面必须写明本规则（见 `docs/tasks/README.md` 规则 5：路径写完整绝对路径）。

### ★ 收口即清：worktree 与验证工作区的常设清理规则（用户 2026-09-18 指令）

清理对象两处：① `/Users/happy/Desktop/opencraft_worktree/`（任务 worktree）；
② `/Users/happy/Desktop/opencraft_scratch/`（PM 验收用的验证树/装置工作区，替代 `/tmp` 的持久盘）。

1. **每卡收口当场清**（默认动作，不是"想起来再清"）：裁决落盘 + 合入后，按三判据删对应
   worktree——**已合入**（`git merge-base --is-ancestor <tip> main`）、**工作树干净**
   （`git status --porcelain` 空）、**证据已入仓**（报告与 `docs/qa/` 随分支合入，无 `/tmp` 孤儿件）。
   scratch 里的验证树直接 `rm -rf`（其重建法写在对应 qa README）。
2. **收口轮盘点**：`git worktree list` + `du -sh` 两目录，凡不属于**在途卡**的一律按三判据清掉。
   长驻白名单只有四样：主仓 `build/`（真人验收入口，不可删）、小体量可复用二进制
   （如注入工具 `ti2input`，~50 KB，源码在 `docs/qa/T-D40-*/tools/` 可重建）、
   第三方校验工具 `opencraft_scratch/mv/`（MagicaVoxel 0.99.6.2，~15 MB，B3/B4 可选加分判据的
   人眼读者，包 sha256 已核、重装法写在 `docs/qa/T-B2-2026-09-18/mv_thirdparty/README.md`）、
   **离线依赖缓存 `opencraft_scratch/deps/`**（~52 MB，= 主仓 `build/_deps/*-src` 去 `.git` 的拷贝；
   外网断时干净检出构建用 `-DFETCHCONTENT_SOURCE_DIR_GLFW=…/glfw-src` 等七个变量指过来完成
   ——2026-09-18 实测，见 `docs/qa/T-B5-2026-09-18/pm_verify/README.md` §1）。
3. **分支拼写异常不构成保留理由**（如历史遗留 `taskT-M2`）——去留只认三判据。
4. `/tmp` **不得充当跨轮工作区**（2026-09-18 系统中途清空一次，三棵验证树+装置+夹具全丢，
   当天重建损失 ≈3 次全量构建；救回全靠"装置原件当轮已提交进 git"）。
5. T-M2 遗留树 `T-M2-mob-ai` 已于 2026-09-18 按本规则清掉（交接文档里"未授权保留"的旧条目同步更正）。

## 7. 跨 agent 派发（2026-09-14 起）

开发者不必在同一个 agent 里跑。实测环境事实：agentmemory 后端（`iii` + `/Users/happy/data/iii-config.yaml`）
监听 **`127.0.0.1:3111`、无鉴权**，数据在单一 `state_store.db`；任何本机 agent 只要挂
`npx -y @agentmemory/mcp`（或直连该 REST）即共享同一份任务板、lessons 与 memories。

跨 agent 的关键**不是**记忆共享，而是**交接契约是否文件化**——本项目已具备：

- **派发**：开发者直接读 `docs/tasks/T<ID>.md`，**无需口述或粘贴提示词**。
- **验收**：报告落 `docs/tasks/T<ID>.report.md`（见 `docs/tasks/README.md` 规则 4），
  PM 读文件验收，用户不必搬运。
- **状态**：`STATE.md` 是唯一权威，任何 agent 可读。

跨 agent 派发时的额外约束：

1. **单写者原则不放松**：跨 agent 的开发者**不得写** `STATE.md`、`docs/` 规格、任何记忆文件；
   只写自己的分支 + 卡面指定的报告文件（见 §5）。
2. **接入新 agent 前先确认它不会自动写记忆**：若该 agent 有 lifecycle hooks 且启用 agentmemory
   自动捕获，会话内容会被自动抽取进记忆层 → P-001 漂移复发（正是我们明确设计要避免的）。
   只允许"可读（lesson recall）不可写"的接入；写 lesson 由 PM 复核后执行。
3. **并发仍用独立 worktree**（§6），根目录固定。
4. **卡面必须自包含**：对方读不到 PM 的记忆文件与对话上下文，卡面即全部依据。
5. **禁止逐字复制 Minecraft Wiki 文本**（CC BY-NC-SA 限制）——只提炼事实与数值，
   用自己的话写，并附来源 URL 与访问日期（见 `docs/04-legal-compliance.md` 红线 4）。
