### 结论速览（一句话版）

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 体素 vs 盒式 | **体素模型（`.vox`）**。每模型 300–800 体素的体量下，盒式组合省下的几个顶点换不来任何东西，而体素模型允许"生物本身是一个可辨认的形体"——**这是原创外观的表达力，不是像不像原版的问题**。 |
| Q2 | 放哪、叫什么 | `assets/mobs/<mob_id>.vox`，**加入 T-A2 已建好的资产根解析**（零新增解析逻辑）。 |
| Q3 | 动画 | **程序化骨骼**：单份网格 + 按关节分组的顶点 + 关节矩阵每帧变换。**朝向只能读模拟值**（`Entity::ai::yaw`），渲染侧不得发明。 |
| Q4 | 加载器 | **自写解析器**（`.vox` 规范是 MIT、格式是定长小端整数、约 200 行）。第三方库 `voxel-io` 许可清白但**自带 4 个第三方 PNG/deflate 编解码器与十几万行无关格式代码**，为读一个无压缩格式引入属于反向优化；`VoxReader` 停更 7 年。 |
| Q5 | 渲染接入 | **`engine/render/**` 一行不改**。客户端新增：专用顶点格式（pos + 逐顶点 palette UV）、一份极小 shader、每类型一份缓存网格。**模拟态模型 → 缺文件时逐像素回退到现有两立方体**。 |
| Q6 | 工作量 | 引擎侧 **≈ 770 行 C++**（1 张卡可交付）；美术侧 **≈ 3–6 小时/生物**（待实测，见 §7.2）。**首发生物建议 Mossback 先做**（体量最简、判定最直观）。 |

1. **MagicaVoxel 是有许可的，PM 的"官网未列明"结论已被推翻**——官网

2. **许可红线不是"工具免费"，是"工具不能是 MC 的资产来源"**。三条 AI 硬规则

   **提示词不得点名 MC**，**`assets/CREDITS.md` 照旧逐条留痕**。
3. **回退是硬要求，且必须逐像素等价**：模型文件缺席是"全新检出"的正常状态。
   路由判据必须是 `mob_models.find(type)` 命中与否——**未命中走的就是现有那条码路**，

## 2. Q1 · 体素模型 vs 盒式组合

### 2.1 两个方案的真实形态

**盒式组合（bone rig over boxes）**：模型 = 若干长方体（头、身、四肢），每个长方体
带一个骨骼枢轴；动画 = 对每个长方体施加旋转矩阵。原版生物走的就是这条路——
但**这一点与我们的选择无关**（`docs/04` 红线 5：观感不逐项对齐，**不得因为"更像 MC"
就选盒式**）。

**体素模型（voxel model）**：模型 = 一组三维格点上的实心体素，每个体素带一个调色板索引；
渲染 = 把体素集合转成表面网格（只保留暴露面），动画 = 把网格**按关节分组**后施加矩阵。

### 2.2 取舍对比

| 维度 | 盒式组合 | 体素模型（`.vox`） |
|---|---|---|
| 顶点数（同一形体） | 极低：n 个盒子 = 24n 顶点，**与形体精细度无关** | 与**暴露面**成正比（见 §2.3 实测） |
| 美术制作成本 | 低，但要**先想清楚分件**；细节靠贴图补 | 低到中：所见即所得，不需要分件（分件由调色板标注，§4.3） |
| 动画表达力 | 强：**任意骨骼层级**、旋转组合自由 | 中：关节数受"分组"限制，但**躯干/四肢/头/尾这类关节完全够用** |
| 形体表达力 | 弱：**非长方体形状做不出来**（触角、喙、尾鳍、蘑菇伞盖要么用盒子近似，要么上贴图） | 强：**任意体素形体**，且天然是"像素风"这个风格类别 |
| 与现有管线距离 | 近（就是现在的两个盒子乘更多） | 中（需要网格生成 + 新顶点格式） |
| "加一种生物"的成本 | 改 C++（新增盒式表） | **放一个文件**（与 T-A2/§1.2 的既有成本模型一致） |
| 与"模型也算美术资产"的裁决 | 模型规格仍散在 C++ 里 | **模型是资产文件**，美术侧可独立迭代 |

### 2.3 体素模型的顶点数：实测，不是估算

用一份一次性脚本解析真实 `.vox` 样本，统计"每个体素 6 个面里没有相邻体素的面"之数量
（即 culled meshing 的面数），再乘 4 顶点 / 2 三角形。样本取自 MagicaVoxel
0.99.6.2 发行包自带的示例模型（**仅用于测量，不进入仓库**）。

原始输出：`docs/qa/T-R3-2026-09-18/qa_vox_geometry_measurements.txt`

| 样本 | 体素尺寸 | 体素数 | 暴露面 | 顶点（4/面） | 三角形 |
|---|---|---|---|---|---|
| `3x3x3.vox` | 3×3×3 | 20 | 72 | 288 | 144 |
| `chr_sword.vox` | 20×21×20 | 334 | 510 | 2 040 | 1 020 |
| `chr_knight.vox`（人形） | 20×21×20 | 398 | 730 | 2 920 | 1 460 |
| `shelf.vox` | 45×45×45 | 1 602 | 6 326 | 25 304 | 12 652 |
| `castle.vox` | 21×21×21 | 2 628 | 3 696 | 14 784 | 7 392 |
| `teapot.vox` | 126×80×61 | 28 411 | 55 964 | 223 856 | 111 928 |

**读法**：一个 **398 体素的人形**（`chr_knight`，尺寸 20×21×20——注意它比我们的
Hollow Wretch 需要的精度高得多）约 **730 面 / 2 920 顶点 / 1 460 三角形**。

**对我们的预算含义**（口径：总顶点数 = 单体顶点 × 同时可见生物数）：

| 同时可见生物数 | 730 面模型的总三角形 | 参照 |
|---|---|---|
| 1 | 1 460 | — |
| 10 | 14 600 | 比一个 16×16 区块的方块网格低一个数量级 |
| 70（T-M2 的刷怪上限） | 102 200 | 与现代游戏的**单个道具**同量级 |

⇒ **顶点数根本不是这个决策的瓶颈。** 结论：**选体素模型**。

### 2.4 代价（必须写清楚，不许只说好处）

1. **需要网格生成**：必须有"体素集合 → 表面网格"的一步（约 150 行，含面剔除）。
   盒式方案不需要这一步。
2. **需要新顶点格式**：现有 `MeshVertex`（`mesher.hpp:76-100`，10 字节、逐顶点 tile 索引 + AO）
   是**区块网格**用的，`crack_vao` 是 **pos+uv、靠 uniform 传 tile**。两个都不能直接装
   一个"每面用不同调色板格"的体素模型（详见 §6.2）。
3. **调色板是唯一的颜色来源**：`.vox` 里体素只存 1 字节调色板索引，颜色在 `RGBA` 块。
   ⇒ 换配色要改调色板 PNG（这是**特性也是约束**，见 §3.3）。
4. **动画上限更低**：体素网格的分组是"每个体素属于哪个关节"，没有骨骼层级。
   对首发的三种生物够用；将来若要做长肢体多段摆动，需回到分组细化。

## 3. Q2 · 模型文件放哪、叫什么

### 3.1 目录与命名

**结论**：

```
assets/
├── blocks/                 ← T-A2，已有
│   └── <block_id>_<slot>.png
├── items/                  ← T-A2，通道已建
│   └── <item_id>.png
├── mobs/                   ← 本卡建议新增
│   ├── mossback.vox
│   ├── hollow_wretch.vox
│   └── blastbud.vox
└── palettes/               ← 本卡建议新增（见 §3.3）
    └── mossback.png
```

**理由**：

1. **`<mob_id>.vox`，一个生物一个文件**——与 `assets/items/<item_id>.png` 逐字同构，
   与 `MobRegistry::string_of()` 的字符串 id 同源；不引入编号（`assets/README.md` §1 已
   写明"数字 id 会随内容卡漂移，字符串 id 稳定"）。
2. **不留 `_top/_side` 之类的 slot 后缀**：体素模型自带三维形体，没有"面槽位"概念。
3. **文件名必须逐字匹配 `mob_id`**（同 T-A2：写错 = 等于没放，静默回退）。

### 3.2 是否纳入 T-A2 的资产根解析

**结论：纳入，且零新增解析逻辑。**

`client::resolve_assets_root()`（`asset_atlas.hpp:71-83`）返回的是**资产根目录**，
`block_tile_path()` / `item_icon_path()` 只是在它下面接一段路径。模型路径只需再写一个
同型函数：

```cpp
// 契约（形状与 block_tile_path 同构）
[[nodiscard]] std::filesystem::path mob_model_path(const std::filesystem::path &assets_root,
                                                   std::string_view mob_id);
// 返回 assets_root / "mobs" / (mob_id + ".vox")
```

⇒ **同一个 `$OPENCRAFT_ASSETS_DIR` → `<cwd>/assets` → `<cwd>/../assets` 顺序，
同一套"缺目录不崩"语义，同一条启动日志纪律。**

### 3.3 颜色从哪来：调色板 PNG（本卡的关键设计决定）

`.vox` 的体素只存**调色板索引**（1 字节），颜色在 `RGBA` 块里（`qa_vox_format_spec.txt`
第 6/7 节）。这给了两条颜色路径：

| 路径 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| (a) 直接烘焙 | 读 `RGBA` 块，顶点直接带颜色 | 最简单，一步到位 | **颜色绕开了 T-A2 的 PNG 通道**：改一个生物的配色要回 MagicaVoxel 重导出 |
| (b) 调色板贴图 | `assets/palettes/<mob_id>.png`（16×16 = 256 格），顶点带 UV 索引到该格 | 颜色走既有 PNG 通道；**改配色不用碰模型**；与 `blocks/items` 同一套规则 | 多一个文件；模型与调色板必须成对 |

**结论：走 (b)，并在加载器里保留 (a) 作为兜底。** 理由：
- `docs/05 §2` 的定位是"模型也是美术资产"，而**颜色是美术资产里最常改的那部分**；
  (a) 会让最常改的东西变成"必须重走导出流程"。
- 调色板 PNG 的形状（16×16）**正好复用 T-A2 的"严格 16×16、不缩放"规则与加载器**——
  连 `load_tile_png()` 都可以直接复用（`asset_atlas.hpp:61`）。
- (a) 兜底的意义：调色板 PNG 缺席时用 `.vox` 内置调色板，`*.vox` 单文件仍然可用
  （对单测与美术侧预览都方便）。

> ⚠ **待校准**：调色板贴图的采样模式必须是 **nearest**（像素风不能插值）。
> 现有图集是 nearest 还是线性，需在实现卡核实 `engine/render/src/rhi.cpp` 的
> `Texture2D` 默认过滤（本文档未核）。

## 4. Q3 · 动画方案

### 4.1 哪些动作需要动画（按"可被玩家观察"的程度排序）

| # | 动作 | 可观察性 | 模拟依据 | 优先级 |
|---|---|---|---|---|
| A1 | **转向 / 看人** | ★★★ 已经存在（现在的"头立方体"唯一的用途） | `ai.yaw`（+`ai.pitch`） | **必须** |
| A2 | **行走摆动** | ★★★ "它在走"与"它在滑"的区别 | `velocity` 幅值 + `on_ground` | **必须** |
| A3 | **受击闪红 / 后仰** | ★★ 反馈手感 | `ai.hurt_cooldown` | 高 |
| A4 | **蓄爆预告**（Blastbud） | ★★★ 生死攸关的信息 | `ai.fuse` | 高 |
| A5 | **死亡** | ★★ 但**无模拟依据**（见 §4.4） | 无 | 中（需先补模拟） |
| A6 | 幼体缩放 | ★ | `ai.baby` | 低（免费，几何缩放） |

### 4.2 体素模型怎么做动画：三个候选

| 方案 | 做法 | 表达力 | 内存 | 文件格式 | 与模拟值的关系 |
|---|---|---|---|---|---|
| **F1 逐帧模型切换** | 用 `PACK` 块存多份模型，每帧换一份 | 高（任意形变） | **差**：N 倍体素数据 | 单文件内含多个 `SIZE`/`XYZI` | 需要"帧 → 时刻"的映射，**渲染侧要自己拿相位** |
| **F2 程序化摆动（无分组）** | 整个模型做正弦摇摆/挤压 | 低（像果冻） | 最好 | **不需要任何额外信息** | 同上 |
| **F3 程序化骨骼（分组）** | 顶点按关节分组，每关节一个矩阵 | 中高（四肢/头/尾/躯干） | 好（**单份几何**，每组一个矩阵） | 需要"哪个体素属于哪个关节"的标注 | 同上 |

**结论：F3。** 理由：
1. **单份几何**——F1 的 N 倍内存对"70 个生物同屏"是实打实的线性放大，而 F3 只有
   每类型一份网格 + 每实例几个矩阵。
2. **表达力对首发生物足够**——Mossback 要"四条腿交替 + 抬头吃草"，Hollow Wretch 要
   "双臂前伸 + 交替迈步"，Blastbud 要"分节胀缩"，全是**关节矩阵能表达的**。
3. **F1 的 `PACK` 路径在现成工具链里不可用**：MagicaVoxel 0.99.6.2 的动画导出走
   **scene graph 的帧索引**（`nTRN` 的 `_f` / `nSHP` 的 `_f`，见
   `qa_vox_format_ext.txt` 第 1/3 节），而不是 `PACK`。**`PACK` 的多模型语义被规范
   标注为 0.98.2 版的动画配套**（`qa_vox_format_spec.txt` 第 4 节），
   现版工具已经不是那条路。⇒ 走 F1 就得解析 scene graph，那是**另一个量级的复杂度**，
   而收益只有"任意形变"。

### 4.3 关节标注怎么做（F3 的关键设计）

需要一个"哪个体素属于哪个关节"的标注。三个候选：

| 候选 | 做法 | 美术侧成本 | 解析侧成本 |
|---|---|---|---|
| (i) 名字前缀 | 每关节一个文件（`mossback_head.vox` …） | 高（要分文件导出 N 次） | 低 |
| (ii) **调色板索引分段** | 约定"调色板索引 1–8 = 关节标签，9+ = 颜色" | **低**（就是"换颜色再画"） | 低（一次查表） |
| (iii) 按连通域自动分 | 几何连通性聚类 | **零** | 高且**不可控**（相邻的腿会粘在一起） |

**结论：(ii) 调色板索引分段。** 具体契约（供实现卡采用）：

```
调色板索引（1-based，与 .vox 的 colorIndex 同口径）
  1..8   关节标签（reserved，8 个够首发生物用）：
            1 = body   躯干       2 = head  头
            3 = arm_l  左前肢     4 = arm_r 右前肢
            5 = leg_l  左后肢     6 = leg_r 右后肢
            7 = tail   尾/附加   8 = reserved（留给将来的"独立摆动件"）
  9..255 颜色槽（关节标签 1..8 的格子**同时**提供该关节的颜色，
          因此美术侧的实际操作是"选一个颜色画一条腿"）
```

**美术侧工作流**（这是这个设计的全部价值所在，必须写清楚）：
1. 在 MagicaVoxel 里先把 8 个关节标签色摆在调色板最前面（索引 1..8）；
2. 画躯干时点索引 1 的颜色，画头点索引 2……**每条肢体一个颜色**；
3. 同一关节内**想用多种颜色**时：这个方案只有一种颜色/关节。
   ⇒ 如果美术侧需要"同一关节多色"，则把标签扩到"索引 1..16 = 关节标签 × 明暗档"
   （每关节 2 档），或改用 (i)+(ii) 混合（关节内多文件）。
   **⇒ 这是我们自己的格式约定，不是外部标准；美术侧一旦反馈不够用就按上面两条扩，
   扩展点已经留出（索引 8 保留 + 分段可平移）。**

> ⚠ **待校准**：8 个关节是否够。首发三种生物的关节数分别是
> Mossback 6（躯干/头/4 腿）、Hollow Wretch 6（躯干/头/2 臂/2 腿）、
> Blastbud 3（躯干/头/足）。**按此估算够用**，但若美术侧要"耳朵/尾巴独立摆动"，
> 需要扩到 16（仍在一个字节内，无格式变更成本）。

### 4.4 与模拟值的关系（★ 本节的硬要求）

**规则：朝向与动作由模拟驱动，渲染侧不得发明朝向。**

具体到字段：

| 量 | 唯一来源 | 渲染侧**允许**做什么 | 渲染侧**禁止**做什么 |
|---|---|---|---|
| 朝向（水平） | `Entity::ai::yaw` | 直接用它构造朝向矩阵 | 自己定义"面向哪"、自己插值出朝向 |
| 俯仰 | `Entity::ai::pitch` | 同上 | 自行推断（如"看向玩家"） |
| 位置 | `Entity::position`（脚底中心） | 直接作为模型锚点 | 任何形式的"渲染侧平滑"若改变了观察到的位置 |
| 行走摆动**相位** | **无**（模拟不提供） | 由 `velocity` 幅值 + **客户端累加的动画时钟**推导 | 不得回写模拟 |
| 受击闪红 | `ai.hurt_cooldown > 0` | 用剩余 tick 数驱动颜色 | 从 `health` 变化差自行推断"刚被打" |
| 蓄爆 | `ai.fuse > 0` | 用 `fuse` 驱动胀缩 | 自己计时 |

**为什么"行走相位只能由客户端时钟推导"不是违规**：模拟侧确实**没有**"步态相位"
（§1.3 已核实字段清单）。相位是**纯呈现量**，且它不影响任何可观察的模拟行为——
但**它的驱动量（速度幅值）必须来自模拟**，这样"移动快的生物腿摆得快"自动成立。
⇒ 判定标准写清楚：**凡是能改变"玩家看到生物在哪里/朝向哪/在做什么"的量，必须来自模拟；
只有"同一位置与朝向下的姿态形变"允许渲染侧推导。**

**死亡（A5）的诚实结论**：现在**做不到**模拟驱动的死亡动画——`kill_mob()` 当场
`erase`（§1.3）。两个选项：
- **D1（本卡建议，无需改模拟）**：死亡仍然"瞬间消失"，但死亡时**生成一批粒子**
  （复用现成的 `client::Particle` 通道，`main.cpp:776-800`）。零模拟改动。
- **D2（需要一张模拟卡）**：给 `Entity` 加 `dying_ticks`，`kill_mob` 改为
  "先进入 dying 状态、结算掉落、N tick 后 erase"。这才有真正的倒地动画。
  **注意这会改变权威侧行为**（实体存活时长、可能的掉落时机），属于模拟卡范围。

### 4.5 动画参数（帧率与幅度）

| 参数 | 值 | 来源 |
|---|---|---|
| 模拟 tick 率 | 20 TPS | `docs/03 §2`（双循环：逻辑定步长 20 TPS） |
| 渲染插值 | partial-tick 插值（两帧之间插值） | `docs/03 §2` |
| 行走摆动频率 | **待校准**（按水平速率换算步频） | 无来源 |
| 摆动幅度（°） | **待校准** | 无来源 |
| 受击闪红时长 | 跟随 `hurt_cooldown`（10 tick，`mob_sim.hpp:127` ⚖） | ✅ 有来源 |
| 蓄爆胀缩时长 | 跟随 `fuse`（30 tick，`docs/01 §6` ⚖） | ✅ 有来源 |
| 死亡时长 | **待校准**（D2 若采纳，原版量级参考不适用于本项目外观） | 无来源 |

> ⇒ **帧率不是"动画文件里的帧率"**：F3 是**逐帧程序化**，没有离散帧率，
> 只有"摆动相位随位置连续变化"。**这是 F3 相对 F1 的又一优势**（F1 才会引入帧率问题）。

## 5. Q4 · 加载器选型

### 5.1 候选

### 5.2 逐条分析

**(a) 自写解析器**

`.vox` 是**无压缩**的定长小端整数格式：`'VOX '` + 版本号(int32) + `MAIN` chunk +
一串 `[4 字节 chunk id][int32 内容长度][int32 子块长度][内容]`（`qa_vox_format_spec.txt`
第 1/2 节的原文结构）。我们只需要读三种 chunk：

| chunk | 作用 | 是否必需 |
|---|---|---|
| `SIZE` | 模型尺寸 (x, y, z) | ✅ |
| `XYZI` | 体素列表：数量 + 每体素 4 字节 (x,y,z,colorIndex) | ✅ |
| `RGBA` | 256 色调色板（**caveat 见下**） | 建议（配合 §3.3 的兜底路径） |
| 其余（`PACK` / `MATL` / `nTRN` / `nGRP` / `nSHP` / `LAYR` / `rOBJ` …） | 全部**跳过** | ❌ 不读 |

**`RGBA` 的索引坑（必须写进实现卡）**：规范第 7 节附了一条易错说明——
`RGBA` 块按顺序读出的第 0 号颜色，对应的**调色板索引是 1 而不是 0**，
两者整体错开一位（到第 254 号颜色对应索引 255 为止）。
⇒ **查表必须写成 `palette[colorIndex]`，且 `colorIndex == 0` 表示"没有颜色"**；
直接把 `colorIndex` 当成区块内偏移使用会整体错一格。
这是**最易犯、且肉眼几乎看不出**的错（错一格只是颜色偏一点，不会报错）。

**解析器的安全纪律**（沿用 T-A2 的"坏文件不崩"精神）：
1. 任何 chunk 长度超出剩余字节 ⇒ **拒绝整个文件**（1 条 WARN + 回退），不尝试部分读取；
2. `XYZI` 的 `numVoxels` 与实际剩余长度不符 ⇒ 拒绝；
3. `SIZE` 的任一维为 0 或超出上限（建议 256，理由：一个 256³ 的模型 = 1 670 万格，
   远超任何生物需要；上限**待校准**）⇒ 拒绝；
4. 体素坐标越出 `SIZE` ⇒ 拒绝（而不是默默钳制）。

**证据（实测）**：用一次性脚本解析 MagicaVoxel 0.99.6.2 自带的 14 个示例模型，
**全部可解析**（`qa_vox_chunk_structure.txt`）。它们的 chunk 构成印证了"跳过无关 chunk"
的必要性——一个 3×3×3 的模型也带 `nTRN`/`nGRP`/`nSHP`/`LAYR`×8/`MATL`×256/`rOBJ`×11，
**无关数据占文件体量的 99%**。只读三种 chunk 是唯一合理的做法。

**(b) `eisenwave/voxel-io`——许可清白，但为我们的用途是反向优化**

| 事实 | 数据 | 来源 |
|---|---|---|
| 许可 | MIT，`Copyright (c) 2020 Jan Schultke` | `docs/qa/.../qa_voxel-io-LICENSE.txt` |
| 语言/标准 | C++17 | 仓库元数据 |
| 规模 | **129 个文件**；`include/voxelio/` 下 50+ 头文件 | 仓库 tree API |
| **自带第三方** | `lodepng.hpp`(92 KB) / `miniz.h`(67 KB) / `miniz_cpp.hpp` / `stb_image.h`(273 KB) | tree API |
| 自带第三方许可 | lodepng = **zlib**（`Copyright (c) 2005-2020 Lode Vandevenne`）；miniz = **public domain**；stb_image = **public domain** | 三个文件头部 |
| 格式覆盖 | VOX/QB/QBT/QEF/SVX/VL32/PLY/PNG/BinVox/CubeWorld/XYZRGB… | `include/voxelio/format/` |
| API 形状 | `class Reader : public AbstractReader`，`read(Voxel64 buffer[], usize bufferLength)` ⇒ **缓冲区 + 结果对象 + 增量读取**；用 `std::unique_ptr` 的 256 色调色板、`std::vector` 的 chunk 信息、`std::unordered_set` 去重哈希 | `vio-vox.hpp`（本机取回，未入库） |

**为什么不选它**：
1. 我们只需要**一个无压缩格式的读取**，而它是一个**多格式读写库**，附送两个
   PNG 编解码器 + 一个 deflate 实现（`lodepng` / `miniz` / `stb_image`）。
   `docs/03 §9` 的依赖表全部是"一个用途一个库"的口径，这里会变成
   **一个用途带进来 4 个第三方库**。
2. **许可登记成本**：`docs/04` 安全做法 5 要求"新增第三方依赖/资产时即时审查
   （提交信息注明许可）"。**全部宽松许可**（`docs/03 §9`）——MIT / zlib / public domain
   三者都宽松，**这一点不构成阻断**，但要在 §9 加 1 行 + 在 `CREDITS` 加 4 条。
3. **与既有代码的风格不一致**：T-A2 对 `stb_image` 的处理是
   "`#define STB_IMAGE_IMPLEMENTATION` 只在一个翻译单元里、只编译 PNG 解码器"
   （`asset_atlas.cpp:10-19` 自述）——**这个项目已经在做"只要需要的那一小块"**。
   自写解析器是这条既有路线的自然延伸，而引入 voxel-io 是反向。
4. **API 形状比我们的需求重**：缓冲区读取 + 结果对象是给"任意大模型流式读取"设计的；
   生物模型是几百个体素。

**(c) `Deins/VoxReader`**：MIT，但仓库**最后推送 2019-04-20**（7 年前），
0 star，且 `LICENSE` 的版权人是**第三人**（`Jim-Eckerlein`）而非仓库所有者——
**来源链本身就需要解释**。不推荐。

### 5.3 结论

**自写解析器。**

- **理由**：格式是定长小端整数、无压缩、只需 3 种 chunk；约 200 行即可覆盖，
  且能精确控制"坏文件不崩"的每一条判定；避免为读 1 个格式引入 4 个第三方库。
- **代价（诚实写）**：解析器是我们自己的代码，**正确性由我们负责**——
  必须有 golden 文件测试（见 §5.4）。
- **规范来源的许可**：`ephtracy/voxel-model` 仓库是 **MIT**（
  `Copyright (c) 2026 ephtracy`，`qa_voxel-model-repo-LICENSE.txt`）——
  ⇒ **照规范实现解析器没有许可障碍**（这正是"格式规范 MIT"相对于"工具闭源"的
  全部意义）。

### 5.4 实现卡的测试要求（必须一起写进卡面）

1. **golden 文件**：仓库内提交**至少一个自制的** `.vox` 夹具（很小的、手写的、
   体素数据可逐字列出的），断言解析出的 `SIZE` / 体素数 / 指定坐标的 `colorIndex`。
   ⇒ **夹具必须是我们自己的**：MagicaVoxel 自带样本**不得进入仓库**
   （它们不是我们的资产，`docs/04` 红线 2 的精神）。
2. **坏输入表**：截断文件 / 头部错误 / `numVoxels` 撒谎 / 尺寸超限 / 坐标越界
   ——每条都断言"返回失败 + 不崩"。
3. **调色板索引 +1 的边界**：专门一条断言针对 §5.2(a) 的索引映射坑。
4. **空模型**（0 体素）⇒ 视为"没有模型"、回退。
5. **`PACK` 多模型文件**：断言"读到第一个模型并忽略其余"（我们不支持逐帧模型切换，
   但**文件里出现 `PACK` 不得导致失败**——美术侧可能从任何来源拿到文件）。

## 6. Q5 · 与现有渲染管线的接入点

### 6.1 总原则

**本卡只做方案。`engine/render/**` 一行不改**（任务卡 §5 明令）。
下面给出的接入点**全部落在 `game/client/src/`**，这是有意的：模型是**呈现内容**，
不是渲染基础设施。

### 6.2 为什么不能直接复用现有两套顶点格式

| 现有格式 | 位置 | 为什么装不下体素模型 |
|---|---|---|
| `render::MeshVertex`（10 字节，pos + 法线/light 打包 + u16 tile + AO） | `mesher.hpp:76-100` | 它是**区块网格**的形状：绑定区块/分桶（`MeshBucket`）、AO 语义、以及 `tile_index(block_id, slot)` 的全局图集契约。用它就要把生物塞进区块网格管线——**收益只有"省一个 VBO"**，代价是把生物与区块的生命周期绑在一起。 |
| `crack_vao`（`a_pos` vec3 + `a_uv` vec2，**tile 走 uniform**） | `main.cpp:193-205` | `u_tile` 是**整个 draw call 一个值**（`shaders.cpp` 的 crack 顶点着色器）。体素模型**每个面**的调色板格不同 ⇒ 装不下。 |

### 6.3 接入方案（建议形状）

**新增一个客户端私有渲染通道**，四件东西：

1. **顶点格式**：`pos` (vec3) + `palette UV` (vec2) + `part id` (uint8)。
   `part id` 用于 §4.3 的关节分组——**它可以是"顶点属性"，也可以是"按关节分组的
   多次 draw call"**；后者更简单（每关节一个 VBO 区段 + 一次 `glDrawArrays`），
   **建议后者**（`part id` 不进顶点格式，落在 CPU 侧的偏移表里）。
2. **shader**：一份极小着色器，与 crack 同构但**逐顶点 UV 而不是 uniform tile**：

   ```
   attribute: a_pos (vec3), a_uv (vec2)        // a_uv 直接是调色板贴图的 UV
   uniform:   u_mvp (mat4), u_part (mat4)      // u_part = 当前关节的变换
              u_tint (vec4)                    // 受击闪红 / 蓄爆用
   ```

   可以**直接复用 `crack_shader` 的 fragment 端**（采样 + alpha discard，见 `shaders.cpp`）
   ——它已经做了"从图集采样 + 透明丢弃"。**接入的实际工作量主要是顶点端与 CPU 侧。**
3. **每类型一份缓存网格**（★ 必须）：网格按 `mob type id` 缓存，
   **不是每帧重建、不是每实例一份**。70 个同种生物共用一份 VBO。
   重建时机 = 资产在启动时读一次（同 T-A2 的"不做热重载"，`assets/README.md` §3）。
4. **每实例的模型矩阵**：位置（模拟）+ yaw/pitch（模拟）+ 每关节矩阵（渲染侧推导）。

### 6.4 逐帧渲染顺序（供给实现卡）

```
对每个 mob（现有 for_each_entity 循环）：
    const ModelMesh *m = mob_models.find(mob.type)      // 启动时构建的缓存
    if (m == nullptr) {  ← ★ 回退分支：走现有两立方体代码，一字不改
        现有代码（mob_skin + 两个立方体）
        continue
    }
    // 模型分支
    base = translate(position) · rotate_y(ai.yaw)          // 位置与朝向都来自模拟
    for each part p in m->parts:
        mvp = projection · view · base · p.pivot_transform · p.rest_transform · p.animation(dt)
        set u_mvp, u_tint; draw p.vertex_range
```

★★ **关键点**：回退分支与模型分支是**两个互斥的代码路径**，判据是
`mob_models.find()` 命中与否。**未命中时执行的代码与今天逐字节相同**——
这是"新模型未就绪时不崩"的**最强形式**（不是"另一条看起来一样的路"）。

### 11.2 逐字引用的边界（哪些情形允许，为什么）

本文档**只对三类文本做逐字引用**，且都有明确理由：

1. **许可名称与版权行**（MIT / GPL-3.0 / zlib / public domain 的规范名称，

   ⇒ **许可文本本身就是为了被复制而存在的**（MIT 要求"许可声明须随副本保留"），
   引用版权行是**履行许可义务**而不是侵权。任务卡 §6 标准 4 针对的是
   **Minecraft Wiki（CC BY-NC-SA）的正文**——wiki 正文在本文档中 **0 处引用**。
2. **术语与 API 名称**（如 `.vox` / `PACK` / `XYZI` / `nTRN` / `NEAREST` 等）：
   这些是**事实性标识符**，不是可受保护的表达。
3. **引用本项目自己的文档时**（`docs/01`–`docs/05` / `assets/README.md` / 代码注释）
