## 1. 架构定位与核心概念辨析

在《Minecraft》（Java 版与 Bedrock 版）的移动系统中，自动通过高低差地形的方案主要存在两条截然不同的技术路线：**台阶步进高度（Step Height / `maxUpStep`）** 与 **主动预测式自动跳跃（Auto-Jump）**。

```
                    ┌─────────────────────────┐
                    │    玩家水平移动受阻     │
                    └────────────┬────────────┘
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
    【静态碰撞滑动: Step Height】    【动态触发机制: Auto-Jump】
    - 原生高度: 0.6 格 (半砖/台阶)    - 针对高度: 0.6 ~ 1.25 格 (完整方块)
    - 机制: AABB Y轴投影直接平移      - 机制: 预测射线检测 + 模拟输入
    - 状态: 保持 Grounded            - 状态: 进入 Airborne (消耗饱和度)
```

- **Step Height（物理步进）：** 属于碰撞响应阶段的被动滑动。当碰撞体积（AABB）水平位移受阻时，物理引擎尝试将 AABB 沿 $Y$ 轴抬升至 `maxUpStep`（玩家默认 `0.6`，马匹为 `1.0`），如果上移后能容纳无碰撞位移，则直接完成“平滑抬升”。

- **Auto-Jump（自动跳跃）：** 1.10（16w20a）引入 Java 版、最早源于便携版（Pocket Edition）的辅助功能。它是一个**客户端驱动的感知-决策-注入系统**。它不改变物理碰撞体的原生抬升上限，而是在检测到前方满足障碍几何条件时，程序化注入一次垂直跳跃冲量。

## 2. 几何碰撞检测与数学模型

自动跳跃的判定逻辑运行在客户端物理 Tick（每秒 20 次，即 50ms/tick）的**输入更新阶段**（在物理积分之前）。

### 2.1 触发前置条件（Gatekeepers）

在发起昂贵的几何求交前，系统评估以下约束矩阵：

| **约束项**  | **条件要求**                             | **失败原因分析**            |
| -------- | ------------------------------------ | --------------------- |
| **基础设置** | 自动跳跃开关为开启               | 功能被用户显式关闭             |
| **状态约束** | `onGround == true`                   | 仅在地表可起跳，浮空状态禁止        |
| **姿态约束** | `!isShiftKeyDown() && !isSwimming()` | 潜行防坠落、潜泳状态屏蔽跳跃        |
| **载具约束** | `!isPassenger()`                     | 载具由独立载具物理控制器接管        |
| **输入约束** | `movementInput.forwardImpulse > 0`   | 只有正向主观移动时触发，禁止后退/静止起跳 |

### 2.2 空间扫描与多重碰撞盒（AABB）预测

当满足前置条件后，引擎沿玩家期望速度矢量 $\vec{v}_{xz} = (v_x, 0, v_z)$ 向前构造扫描体积。设玩家当前坐标为 $P_0$，碰撞盒为 $B = [-w/2, 0, -w/2] \times [w/2, h, w/2]$（其中 $w=0.6, h=1.8$）。

```
        Y
        ▲
        │                      [Clearance Box] (Head Room: Y + 1.2 ~ 1.8)
    2.0 ┼                 ┌────────────────────────┐  ← 判定顶部是否有阻挡
        │                 │                        │
    1.0 ┼ ── 障碍物高度 ──┼──────────┐             │
        │                 │ 阻挡区域 │             │
        │                 │(Obstacle)│             │
    0.0 ┼─────────────────┴──────────┴─────────────┴─────► Z/X
       P0 (当前位置)        [Foot Box] (Scan: 0.6 ~ 1.25)
```

1. **水平阻挡探测（Foot Probe）：**
   
   构造前向预测盒 $B_{pred} = B + (\vec{v}_{xz} \cdot \Delta t)$。系统查询世界碰撞体，检测足底至 $0.6$ 格高度内是否存在相交图元。若无碰撞，说明当前仅需原生 Step-Up 即可通过，跳过计算。

2. **台阶高度截断（Height Window Verification）：**
   
   当检测到水平阻挡时，算法在碰撞面法线方向寻找障碍物顶面高度 $H_{obs}$。该高度必须严格落入跳跃有效窗口：

  $$H_{step} < H_{obs} - Y_0 \le H_{max}$$

  *标准常数设定：$H_{step} = 0.6$（步进高度阈值），$H_{max} = 1.25$（标准单次跳跃覆盖高度）。*

3. **净空检测（Clearance Check）：**
   
   以 $P_0 + (0, H_{obs}, 0) + \vec{v}_{xz}$ 为基点，向上拉伸 $1.8$ 格构造检测盒，确保障碍物上方没有阻挡物（如倒挂楼梯、低矮天花板）。若有阻挡，立即终止，防止撞头顿挫。

### 2.3 运动方向与碰撞面法向量对齐

为避免玩家沿墙壁侧向滑动摩擦时产生假触发，系统引入移动向量与障碍物几何表面的点积运算：

$$\cos\theta = \frac{\vec{v}_{xz} \cdot \vec{n}_{wall}}{\Vert{}\vec{v}_{xz}\Vert{} \Vert{}\vec{n}_{wall}\Vert{}}$$

- 若法向量与输入速度夹角接近 $90^\circ$（即 $\vert{}\cos\theta\vert{} < \epsilon$），判定为**贴墙侧向平移**，抑制自动跳跃。

- 只有当逆向正对分量超过设定容差阈值时，确认满足越障意图。

## 3. 动力学注入与状态机流转

当判定管线返回 `TRUE` 时，引擎直接接管输入状态机，模拟玩家敲击空格键并附加微调参数。

```
[检测通过] 
    │
    ├─► 设置状态: 跳跃输入置为 true（等价于玩家按下跳跃键）
    ├─► 注入垂直速度: Vy = getJumpPower() ≈ 0.42 m/tick
    ├─► 水平动量微调: 沿视线/移动方向追加微量加速度 (Sprint 乘区)
    └─► 触发消耗: 增加 Exhaustion (饱和度/饥饿度消耗，同常规跳跃)
```

### 3.1 离散时间步进下的抛物线积分

在典型的物理 Tick 中，垂直运动遵循半隐式欧拉积分（Semi-implicit Euler Integration）：

$$v_{y}^{(t+1)} = (v_{y}^{(t)} - g) \times \mu_y$$

$$Y^{(t+1)} = Y^{(t)} + v_{y}^{(t+1)}$$

- 重力加速度 $g = 0.08 \text{ blocks/tick}^2$

- 空气垂直阻力衰减因子 $\mu_y = 0.98$

- 起跳瞬时冲量 $v_y^{(0)} = 0.42 \text{ m/tick}$（跳跃提升效果 `Jump Boost` 每级增加 $0.1$）

在没有外力干扰下，玩家的抛物线在第 4 个 Tick 达到顶点（约 $1.252$ 格），正好掠过高度为 $1.0$ 的障碍物上表面并落入其上表面碰撞体范围。

## 4. 渲染管线、动画呈现与视觉痛点

自动跳跃饱受硬核玩家诟病的核心原因，在于其**视觉平滑机制（Lerp）与非预期起跳之间产生的感官冲突**。

### 4.1 渲染帧与物理帧的解耦（Partial Ticks Interpolation）

Minecraft 物理运算固定在 20 Hz，而渲染帧率通常在 60~240 Hz 甚至更高。渲染器通过 `partialTick`（取值 $[0.0, 1.0)$）进行线性内插（LERP）：

$$P_{render} = P_{prev} + (P_{curr} - P_{prev}) \times \alpha_{partialTick}$$

```
物理 Tick N (起跳)                                  物理 Tick N+1
   │                                                   │
   ▼                                                   ▼
Y = 0.00 ──────────┬───────────┬───────────┬──────── Y = 0.42
 (地面)            │           │           │
             Render Frame 1 Render Frame 2 Render Frame 3
             (α = 0.25)    (α = 0.50)    (α = 0.75)
             Y = 0.105     Y = 0.210     Y = 0.315
```

### 4.2 视角晃动与动画合成（View Bobbing & Camera Offset）

摄像机在第一人称渲染时的最终变换矩阵，由多个子模块复合而成：

1. **世界坐标变换：** 基于 $P_{render}$ 的绝对平移。

2. **走动摇晃（View Bobbing）：** 依赖累积距离参数 `walkDist`。

  $$Bob_{pitch} = A \cdot \sin(k \cdot \text{walkDist})$$

  $$Bob_{roll} = B \cdot \cos(2k \cdot \text{walkDist})$$

  *跳跃起跳瞬时，`onGround` 变更为 `false`，步行晃动曲线在当前相位被冻结或衰减，转而叠加跳跃下压动势。*

3. **视觉阶跃失谐（The "Jarring" Visual Spike）：**
- **手动跳跃：** 玩家大脑在按下空格前拥有“前馈控制（Feedforward Control）”，预期了视角的垂直加速度。

- **自动跳跃：** 算法触发带有数毫秒的前向扫描提前量。当玩家尚未感知障碍接触时，突然施加 $0.42$ 的垂直初速度，视网膜上产生非预期的垂直光流加速（Optical Flow Jitter）。

- **近距离微小跳跃问题：** 面对仅 $0.6$ 到 $0.8$ 格的高低差，系统仍分配常规完整跳跃的 $0.42$ 动量，导致玩家在越过小阶梯时“高高弹起”，出现不符合重力视觉直觉的漂浮感。

## 5. 架构级权衡：Auto-Jump vs. 动态 Step Height

为什么 Mojang 不直接把玩家的 `stepHeight` 提高至 1.0？该设计决策反映了底层游戏机制的系统性冲突：

| **评估维度**    | **Auto-Jump 机制（现行方案）**      | **修改原生 Step Height 至 1.0m**      |
| ----------- | --------------------------- | -------------------------------- |
| **状态转换**    | 触发标准的 `Airborne` 空中状态       | 始终保持 `Grounded` 地面状态             |
| **战斗机制影响**  | 滞空期间触发重击/下落暴击判定，受到击退时易被连击   | 无法触发浮空暴击，地面连续贴地削弱战斗纵深            |
| **体力/食物消耗** | 产生 `Exhaustion`（跳跃衰减饥饿度）    | 零跳跃惩罚，疾跑越障成本与平地完全一致              |
| **机关交互阻断**  | 可跃过绊线钩（Tripwire）、压板；激活上层压力板 | 强行滑过无法阻断射线碰撞，穿透低位红石防线            |
| **网络同步代价**  | 客户端向服务端发包标准跳跃位移，天然兼容原版反作弊   | 极高几率触发反作弊的 `Speed/Fly/Step` 越界检测 |

## 6. 现代演化与工业级优化思路

在现代版本及流行 Client-Side 优化模组（如 StepUp、Sodium 相关生态）中，该机制获得了长足的进化：

- **属性化（1.20.5+）：** Mojang 将步进逻辑从硬编码抽离为实体属性 `minecraft:generic.step_height`。创作者已可通过数据包（Datapack）直接赋能丝滑上台阶，而无需依赖自动跳跃的冲量注入。

- **自适应跳跃冲量调制（Adaptive Impulse）：**
  
  优化方案不再固定施加 $0.42$ 恒定速度，而是根据扫描测得的障碍精确垂直高差 $\Delta H = H_{obs} - Y_0$，反解所需初速度方程：

  $$v_y^{(init)} \approx \sqrt{2 \cdot g_{eff} \cdot \Delta H}$$

  通过对极低台阶施加较小初速度，显著缓和第一人称镜头的顿挫颠簸。

- **摄像机垂直弹性阻尼（Spring-Damper Lerp）：**
  
  逻辑碰撞体依然采用刚性跳跃处理，但渲染相机的 $Y$ 轴偏移接入二阶弹簧阻尼系统（Critically Damped Spring System），将原本阶跃式的垂直折线过滤为平缓的 S 型上升曲线，消除视界光流抖动。
