## 2. 接口契约

### 2.1 单一伤害入口（消除三条路径的不一致）

现状是三处各自扣血。**本卡引入一个统一的伤害应用点**，取代现有三处：

- 摔落：`/Users/happy/Desktop/opencraft/engine/physics/src/player_physics.cpp:483`
- 生物/爆炸事件：`/Users/happy/Desktop/opencraft/game/client/src/tick.cpp:534`
- 读档恢复：`/Users/happy/Desktop/opencraft/game/client/src/main.cpp:253`（这处不是伤害，但需受 §2.4 约束）

要求：
1. **HP 一律钳到 `[0, 20]`** —— 摔落那条裸减法现在会产生负数，必须消失。
2. **HP == 0 ⇒ 进入死亡态**，且**幂等**（已死状态下再受伤害不得重复触发掉落）。这一条是本卡最容易错的地方：生物 `MeleeHit` 事件是每 tick 都可能到达的流（`tick.cpp:530` 的 `for` 循环），若不幂等会每 tick 掉一次物品。
3. 摔落伤害的**数值语义不得改变**：`floor(fallen - 3)`，阈值 `cfg.fall_damage_offset = 3.0`（`engine/physics/include/opencraft/physics/physics_config.hpp:123`）。既有单测 `tests/test_player_physics.cpp:206`（10 格摔 → health 13.0）、`:221`（3 格不扣）、`:234`（落水不扣）**必须继续全绿**。

> ⚠ 冻结项：`engine/physics/**` 是历次卡面的冻结域。**允许**你改 `player_physics.cpp:483` 这一处（把它改为走统一入口 + 加下界钳制），**不允许**改动该文件其它部分、也不允许改 `physics_config.hpp` 的任何数值。

### 2.2 死亡态的存放位置

死亡态是**玩家状态**的一部分。玩家的 `health` 现住在 client 侧 `PlayerState`
（`/Users/happy/Desktop/opencraft/engine/physics/include/opencraft/physics/player_state.hpp:43`）；
权威侧 `WorldSim` 不知道玩家有血量（`protocol.hpp:152-157` 明写这是 T-A1 刻意的临时不对称，M3 才上收）。

⇒ **本卡延续这个既有分割**：死亡态放 client 侧，与 `health` 同处。
**不要**把玩家血量上收到 `WorldSim`——那是 M3 的工作，本卡做会与 M2b 的架构裁决冲突。

新增字段建议落在 client 侧玩家状态附近（具体类型/命名由你决定）：
- `bool dead`（或等价枚举）
- 死亡时的位置（用于掉落落点）

### 2.4 重生点 —— ⚠ 这里有一个陷阱，务必先读

**`ctx.spawn_pos` 不能当重生点用。**
`/Users/happy/Desktop/opencraft/game/client/src/main.cpp:143-150`：存过档后，`spawn_pos` 直接取 `stored_level->player_x/y/z`（上次退出位置），`find_spawn()` 再也不被调用 ⇒ **它会随玩家漂流**。

⇒ 本卡需要**一个独立的 respawn point**。最小做法（推荐）：
- 新档：`WorldSim::find_spawn()`（`/Users/happy/Desktop/opencraft/game/server/sim/src/world_sim.cpp:584`）的结果，落盘进 `LevelData` 的 `spawn_x/y/z` 字段——**该字段已存在**（`game/server/storage/include/opencraft/storage/level_file.hpp:43-45`），只是目前被写成了玩家位置（`tick.cpp:45-47`）。
- 读档：不要再用玩家位置覆盖它。

**同时必须解决"0 血存档自杀"**：`level_file.cpp:71` 写 `health`，`main.cpp:253` 读回，玩家以 0 血开局且无恢复途径。
**最小闭环做法**：读档时若 `health <= 0`，按"重生"处理（传送到 respawn point + HP 回满 20），而不是恢复成 0。
（**不要**为此做库存序列化——那是 `docs/01 §5` 的 M2c 持久化工作，单列。）

## 5. 验收标准

**构建**：`cmake --build build -j` 零错误零警告增量；**测试**：`ctest` 全绿。

1. **存量不回归**：既有 **410** 个 `TEST_CASE`（40 个 `test_*.cpp`，另有 22 个 `SUBCASE`）
   **全绿，且测试文件零改动**。
   ⚠ 本卡**不是**纯重构卡，所以允许新增单测——但存量一律不得改。
2. **HP 钳制**：摔落 30 格后 `health == 0.0`，**不得为负**（单测断言）。
3. **三条路径统一**：摔落致死 / 生物 `MeleeHit` 致死 / 读档 0 血，**三条路径都必须进入死亡态**（单测各一条）。
4. **死亡幂等**：已死后连续 100 tick 施加伤害事件 ⇒ 掉落物数量**不变**（单测断言；这是本卡最容易错的点）。
5. **掉落数量**：装满 N 个非空槽的库存死亡 ⇒ 权威侧生成 N 个掉落物，client 库存清空（单测）。
6. **重生**：点重生 ⇒ 位置 = respawn point、`health == 20.0`、库存为空。
7. **respawn point 不漂流**：死亡重生后连续存读档两次，respawn point **保持不变**（验证 §2.4 陷阱已规避）。
8. **0 血存档自恢复**：手工把存档 health 置 0（或走死亡路径存盘）→ 重进 ⇒ 玩家以满血在 respawn point 开局，**不是 0 血**。
9. **死亡态屏蔽交互**：死亡状态下挖/放/攻击/移动**全部无效**（单测 + 实机）。
10. **实机证据（必须，不可只用单测）**：
    `docs/05 §3.1` 第 5 条——渲染/UI 类缺陷单测覆盖不到。至少录到：
