## 裁决 1：`docs/03 §1.1` 补第 5 个动词 `stream()` —— **采纳，PM 落盘**

并写明：逐区块的 `ensure_chunk` / `unload_chunk` 已收为 private，
客户端**连编译期都调不到**（延续 T-A1 的"编译器保证"范式，这是加分项）。

## 裁决 2：滞回量 2 区块 —— **只记备忘，不进规格**

开发者倾向"只记备忘"，**采纳**。
理由：它是可调常量，不是 ⚖ 对齐数值；进规格会把"调参"变成"改规格"。
**记入备忘**：`kUnloadHysteresis = 2`（`unload_radius - generate_radius`）。

## 裁决 3：持久化是否拆成独立动词 —— **不拆，维持现状**

开发者的理由成立且重要：**"先落盘后释放"的顺序由权威侧一处保证**。
拆成独立动词后，调用方就可能先调 `unload` 再调 `persist` ⇒ **丢数据**。

**裁决：维持 `stream(persist=true)` 的现形态。** 这正是"把约束编码进接口形状"
而不是写进文档的又一例（与 T-A1 的 private 写入口同思路）。

## 裁决 4：`StreamRequest` 运行期保护（`unload_radius = 0` 尖锐边）—— **采纳，加断言**

`unload_radius == 0` 意味着"保留中心一格，其余全卸"，误用会灾难性丢数据。
开发者已主动指出这条尖锐边（记功）。

**裁决：加运行期保护**（断言或 clamp）。但注意：
- 生产路径**不得**因保护而静默改变语义；
- 建议 **debug 断言 + release 下 clamp 到 `>= generate_radius`**，并在报告中说明。

> 由后续卡或本卡的补丁落实，**登记为 T-D33**（低优先，因当前调用方由
> `client::make_stream_request` 统一构造，误用风险已降低）。

## 备注：本卡开发者的接口设计倾向值得记

连续两张卡（T-A1 / T-D4）都体现了同一个手法：
**把架构约束编码进类型系统/访问说明符/接口形状，而不是写进注释或文档。**
- T-A1：写权限 → `private` + 私有嵌套类
- T-D4：不得直调 → `private`；顺序约束 → 单动词 `stream()` 内部保证

**这应作为后续架构卡的默认范式**（PM 已记入裁决，将写进 `docs/03`）。
