### ★ 核心主张经 PM 亲自验：写权限确实由**编译器**保证

开发者称"唯一写权限由编译器保证，不是约定"。PM 核查 `world_sim.hpp`：

```
157: private:
165:   void write_block(...);
174:   void set_fluid_at(...);
178:   bool place_water_source(...);
184:   bool remove_water_source(...);
205:   class FluidWorld final : public voxel::IFluidWorld {   // 私有嵌套类
213:     void set_fluid_at(...) override { sim_->set_fluid_at(...); }
```

四个写入口全在 `private:`；流体的 `set_fluid_at` 由**私有嵌套类**实现，
**外部连引擎 `IFluidWorld` 要求的接口都拿不到**。**主张成立。**

客户端 `WorldSource` 退化为全 const 视图，只持 `const WorldSim*`，
渲染/物理/射线/HUD 的调用签名一行未改。

**额外加分**：他还顺手 `= delete` 了 `WorldSim` 的拷贝与移动（第 59-62 行）——
修掉了自己 S-5 里指出的"旧 WorldSource 可拷贝且内含自指 FluidSim"隐患。**未等 PM 裁决就先加固，正确。**

## 裁决 S-1：**追认** `ActionRequest::ActorPose`

权威侧要判"超出到达距离"就必须有玩家位置/高度/眼高，而权威侧手上没有玩家状态。
扩充请求结构**是必要的**，不是越界。

**追认。** 并且这正是"请求须为值语义、可序列化数据"这条约束的正确体现
（玩家状态以**数据**形式随请求传递，而非让权威侧反向持有客户端状态）。
PM 落 `docs/03`。

## 裁决 S-2：**PM 卡面自相矛盾，开发者理解正确**

卡面把"库存改动"列为动作之一，但建议结构里只有 `item_or_block`（一个 u16）——
**两者不自洽**（这是 PM 第 4 次同类疏漏：T-M1 两次、T-I1 一次、本卡一次）。

**裁决：按开发者理解执行** —— 库存留客户端，M3 随"玩家/会话"一起上收。

理由：库存上收需要"玩家身份/会话"概念，而本卡明确不做玩家管理与会话管理。
现在上收库存会连带把 M3 的范围拖进来，违反"一次做两件事会不可验收"。
**登记为 M3 必做项**（见下方 S-5）。

## 裁决 S-3：链接期 duplicate libraries 警告 1 → 2 条 —— **保留显式依赖**

开发者问：保留（显式依赖可读）还是改纯传递依赖？

**裁决：保留。** 理由：
- 该警告是**既有噪声**（T008 基线就有 1 条），不是本卡引入的新问题类别；
- `opencraft_sim` PUBLIC-link 显式依赖，对"权威侧需要什么"是**自文档**；
- 改成传递依赖会让依赖关系变隐含，得不偿失。

但**须在报告中固定"当前 2 条 = 预期"这个基线**，避免后续卡误判为回归。

## 裁决 S-4：挖掘日志 —— **不开小卡，并入 M3 反作弊上收**

开发者问：挖掘成功没有常驻日志，是否单开"挖掘日志"小卡？

**裁决：不开。** 理由：
- 这是**可观测性**需求，单独开卡收益低；
- 真正的痛点是"挖掘计时仍在客户端"（M3 反作弊须上收）——
  上收时自然会带出日志。**并入 M3 必做项**。

本卡用"临时打点 → 取证 → 还原"拿到证据（`strings | grep HARNESS = 0` 已证无残留），
手法合规，处置正确。
