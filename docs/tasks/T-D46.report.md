## 4. 设计与判断留痕（PM 复核要看的四处）

### 4.1 窗口与护甲的先后次序（契约未写，按原版次序）

原版是"**先用原始伤害比窗口，再对结算出的差值套护甲**"（`LivingEntity.hurt` 的 `actuallyHurt(amount - lastHurt)`）。
本卡照此：`settle_hurt(原始 amount)` → `damage_after_armor(结算值)`。
实机日志印证：被吞的一击打印的是**原始 3.0**（`absorbed ... last 3.0`），穿甲后的落地量是 2.34。

### 4.2 摔落：命中 ⑤ 的豁免，但不吃 ① 的窗口

`take_fall_damage` 现在也走 `damage_after_armor(..., DamageType::Fall, ...)` —— 因为 `Fall` 在豁免表里，
返回值恒等于原伤害，**观测行为与 T-D45 完全一致**（既有摔落用例全绿）。这样做的好处是"绕甲"是一条**表项**而不是
"漏写了一次调用"，单测 6 才能真的把它钉住（删掉豁免就会红）。
⚠ **窗口不作用于摔落**：卡面 §1.1 明写"本卡不碰玩家扣血路径"，且 §5.2 只要求豁免绕甲。原版对摔落也是走窗口的
（`BYPASSES_COOLDOWN` 在 1.20 是空集）⇒ **这是一处有意与原版不同的地方**，登记在「需 PM 裁决项」④。

### 4.3 ★ `MeleeHit` 事件的 `position` 改成"攻击者位置"

**为什么必须改**：契约 ⑥ 要求玩家被推，而"往哪推"需要攻击者的位置；事件是客户端唯一的通道（玩家不是权威侧实体，
查不到）。原版 `ActorEvent` 只有 4 个字段，`protocol.hpp` **不在白名单**，加不了字段。

**改法与配套**：事件改为携带**攻击者自身脚下**（与 `Explosion` 一直携带"爆心"同义）；客户端把
`take_damage` 的"尸体位置"参数改成**玩家自己的脚下**，所以**死亡掉落落点没有移动**（T-D45 语义保持：
掉落落在玩家死处，不是伤害来处）。日志里 `mob melee for X at (...)` 的坐标随之从"玩家脚下"变成"攻击者脚下"。

**存量影响**：三条读事件的断言只读 `kind/amount/source_type`（已 grep 确认），**零翻转**。
**遗留**：`protocol.hpp:180` 的 `position` 注释（`// where it happened (impact / blast centre)`）对近战那一半过时了，
该文件不在白名单 ⇒ 请 PM 落一行注释修正（「需 PM 裁决项」②）。

### 4.4 生物侧击退的"是否落地"判据

`damage_mob` 只返回"死了没有"，窗口吞掉的一击与落地的一击在返回值上无法区分。为避免**复制**它的判定（契约 ⑦ 的
反面），`apply_attack` 读的是 **`damage_mob` 自己移动过的血量**：

```cpp
const double health_before = mob->health;
const bool died = damage_mob(...);
if (mob->health < health_before && !died) { knock_back(*mob, req.actor.feet, kAttackKnockback); }
```

这是"读结果"而不是"重算规则"，两侧（生物/玩家）的击退门控因此完全一致：**只有落地的一击才推**。

## 6. 回答卡面点名的两个问题

**§7.6 空手打死一只 20 血量的 Hollow Wretch 需要几下？**
**20 下**（`kPunchDamage = 1.0`，生物 20 点生命）。时间上还要乘攻击节奏：客户端左键冷却 **12 tick**（`tick.cpp`
的 `attack_cooldown = 12`），生物的受击窗口是 10 tick ⇒ 每一次挥击都恰好落在窗口之外、**每一下都全额结算**，
所以是 20 × 12 tick = **240 tick = 12 秒**（不含走位/生物逃跑）。若生物在此期间被别的伤害打过，窗口会吞掉 ≤ 原伤害的挥击，
实际会更慢。⇒ 与卡面 §2.3 的提醒一致：**徒手伤害 1.0 目前是全表唯一伤害源**，工具伤害（木剑 4 起）仍是后续卡；
本卡让"护甲有多强"变得可算，但**玩家对生物的手感仍然偏软**（12 秒一只），建议后续"工具伤害/攻击充能"卡优先。

**§7.2 有没有比改 `ItemDef` 更轻的方案？**
评估后**仍按 C-5 建议改 `ItemDef`**，理由：① 护甲点与韧性是"这个物品是什么"的静态属性，与已有的 `equip` 同性质；
② 旁挂一张"物品 id → 护甲值"的表会让同一份物品清单存在两处、必须同步（本项目"一条规则一个源"的纪律）；
③ 代价实测很小：`ItemDef` 每条 +16 字节、全表 38 条，编译面虽大但**零运行时开销**，且 `register_item` 的聚合初始化
只需在调用点补两个字段（`LaunchItem` 的新字段带默认值 0，其余 33 条一个都没动）。
**§7.5 的缓存问题**：采用**每次结算实时读四格**，不缓存；理由是缓存需要被"死亡掉落/重生/读档/未来装备界面"四条
写路径同时失效，而实时读只有 4 次数组读 + 4 次注册表查（一次命中最多一次，生物近战冷却 20 tick）。
