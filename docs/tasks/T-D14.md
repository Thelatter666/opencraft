## 目标（一段话）

实现 Minecraft Java Edition 1.10+（16w20a）的 **Auto-Jump**：客户端每个逻辑 tick 在**输入阶段**
（物理积分之前）做前向几何扫描，当玩家在地面上、向前移动、且前方存在**高度落在 (0.6, 1.25] 窗口**
的障碍、且上方净空足够时，**自动注入一次跳跃**（等价于按空格），让玩家无需手动按键即可跨上
**1 格整方块**的坎。

**它不改变 `step_height`**（玩家仍为 0.6，`PhysicsConfig::step_height` 一字节不改）。

## 为什么（用户原话与裁决链）

用户 2026-09-15 实机验收 T-D8 后反馈：

> "上台阶这个过程的动画效果做得很烂……像是**瞬移上去的一样**，而原版 MC 有一个
> **跳跃**的动作，非常自然。"

- T-D13 已消除"瞬移感"（摄像机弹簧阻尼），但**1 格坎仍需手动跳**——这是 MC 原版行为。
- 用户裁决方向：**对齐 MC，另立 Auto-Jump 卡**（STATE.md 任务表 T-D14）。
- ⚠️ **关键背景**：玩家 `step_height = 0.6 < 1.0`，故 1 格整方块手动跳是**正确的 MC 行为**
  （已裁决维持 0.6，见 `docs/tasks/T-D8.ruling.md` S-1）。要"1 格坎也能自动过"，
  正确机制是 Auto-Jump，**不是**放宽 step height。本卡**不得**改 `step_height`。

## 接口契约

### 1. 新增纯函数（**必须**，仿 `fov.hpp` / `camera_spring.hpp` 先例）

把判定做成**纯函数**放在可测的头文件里，让门限/窗口/净空可以被单元测试逐条断言，
而不是只能在实机里看。建议（命名自定，但须满足下方契约）：

```cpp
// engine/physics/include/opencraft/physics/auto_jump.hpp （建议路径，属白名单）
namespace opencraft::physics {

struct AutoJumpConfig {
    // 高度窗口 (step_height, max_clearable]：低于下界由 step-assist 处理，
    // 高于上界单次跳跃够不着（research/08 §2.2）。
    double min_obstacle_height = 0.6;
    double max_obstacle_height = 1.25;
    // 前向扫描距离（沿水平移动方向），建议 0.6~1.0 格量级，自定并说明。
    double scan_distance = 1.0;
    // 净空检测高度：障碍顶面之上须留出玩家身高（research/08 §2.2 写 1.8）。
    double clearance_height = 1.8;
    // 贴墙误触发抑制：移动方向与墙面法线夹角判定的容差（research/08 §2.3）。
    // |cos θ| 小于此值判定为"贴墙侧向平移"，不触发。
    double wall_normal_epsilon = 0.05;
    // 总开关（对应设置项；false 时 should_auto_jump 恒 false）。
    bool enabled = true;
};

// 判定：本 tick 是否应注入一次自动跳跃。纯函数，无隐藏状态。
//   state  — 当前（tick 头）玩家状态
//   input  — 本 tick 的输入采样
//   world  — 世界查询
//   cfg    — 物理参数（读 step_height / jump_velocity 等）
//   aj     — Auto-Jump 参数
[[nodiscard]] bool should_auto_jump(const PlayerState &state, const InputState &input,
                                    const IBlockSource &world, const PhysicsConfig &cfg,
                                    const AutoJumpConfig &aj = AutoJumpConfig{});
}
```

> 你**可以**自由调整上面的字段名/拆分方式/结构体形状（例如把结果做成带 `reason` 的出参
> 便于测试断言"为什么不触发"），**但必须**满足：
> ① 纯函数、可单测；② 世界查询只走 `IBlockSource` 既有虚函数，**不得**给 `IBlockSource`
> 新增虚函数（会破坏 T-D7 冻结的适配器契约）；③ 不修改 `step_player` 的前四个参数。

### 2. 冻结项（不得改动）

- `step_player(...)` **前四个参数签名不变**（T-D7 冻结契约）。
  `MoveResult *result` 仍是唯一扩展点——**允许**你在 `MoveResult` 里**追加**
  `bool auto_jumped = false;` 之类的字段（只加字段，不改既有字段语义）。
- `IBlockSource` **不新增虚函数**。判定所需的碰撞查询请复用：
  - `solid_at(wx, wy, wz)`
  - `shape_top_at(wx, wy, wz)`（已有默认实现；接顶面高度时用这个）
  - 若需要非空判定，用 `shape_top_at(...) > 0.0`
- `PhysicsConfig::step_height`（0.6 / 生物 1.0）、`jump_velocity`（0.42）、
  `gravity`（0.08）、`vertical_drag`（0.98）**一字节不改**。

### 3. 注入方式（关键）

**不要**直接写 `state.velocity.y = 0.42`。
正确做法是在 `step_player` **之前**把 `InputState::jump` 置为 true，让已有的跳跃分支
（`engine/physics/src/player_physics.cpp:545` `if (in.jump && s.on_ground && !water)`）执行。
这样：
- 跳跃语义（含疾跑的 `sprint_jump_boost` +0.2 冲刺加成）与手动跳**完全一致**，无需复制逻辑；
- 黄金回放与 ⚖ 数值自动保持一致。

若你判断在 `step_player` 内部注入更合适（例如为了 M3 服务端权威），**必须在报告中
说明理由并取得 PM 同意**——默认按"客户端在输入阶段置 `in.jump`"实现。
