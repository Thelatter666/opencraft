## 背景：为什么开这张卡

用户 2026-09-14 实机试玩后反馈：**"人物移动这一块有很大瑕疵"**，要求后期重点开发，
并指定本卡应**自主上网调研 Minecraft 的移动手感、双击 W 疾跑机制、疾跑时的 FOV 切换**。

已知的客观差距（来自 T007/T008 报告，供你起点参考，不作为调研范围的边界）：

- **疾跑跳均速未对齐**：规格要求 7.127 m/s，但 T007 的空中模型把稳态锚定在**步行**速度
  （`a_air = walk·(1−0.91)`），疾跑跳在空中向步行速度衰减 → 达不到 7.127。
  T007 报告自述"疾跑跳 +0.2 位移增益未做"。
- **双击 W 疾跑未实现**：T008 客户端只支持按 Ctrl 疾跑（按住前进 + 疾跑键）。
- **疾跑 FOV 已实现但未对账**：T008 做了"平滑拉伸"，数值与过渡曲线未与 MC 核对。
- 其他已知短板（**本卡不修，但要求你调研后写入 gap 清单**）：半砖/楼梯碰撞形状缺失、
  游泳出水笨拙、无梯子/藤蔓攀爬、`InputState` 缺 backward 字段。

## 调研任务（本卡的核心要求）

**目标**：把"移动手感"从"照规格抄数值"提升为"理解机制后对齐行为"。

1. **允许的来源**（`docs/04-legal-compliance.md` 红线 1/4）：
   - `minecraft.wiki` 的**事实与数值**（不得逐字复制其文本，只提炼数字并用自己的话写）
   - 公开技术文章、开发日志、社区讨论（**只看思路，不抄代码**）
   - 官方更新日志/公告
2. **禁止**：反编译 Minecraft、参考 MCP/Yarn 等映射产物、把反编译代码喂给 AI 再搬回来。
3. **必须交付**（新建 `docs/research/05-mc-movement-feel.md`）：
   - **双击 W 疾跑**：双击窗口的精确时长/tick 数、启动条件（是否要求前进键、是否要求地面）、
     停止条件（松开前进、松开疾跑键、撞墙、饥饿门槛）、与 Ctrl 疾跑的关系
   - **疾跑 FOV**：基础 FOV、疾跑时的修正量（倍率或百分比）、过渡时长/曲线、
     是否随速度连续变化、是否有独立设置项可关闭
   - **疾跑跳**：跳跃时的额外水平增益（若有）、空中动量保留规则、疾跑跳均速 7.127 m/s 的构成
   - **空中控制**：空中加速度与地面加速度的比例、二者阻尼差异
   - **饥饿交互**：疾跑的最低饥饿值、疾跑/疾跑跳的耗竭值
   - 每条数值**必须附来源 URL 与访问日期**；来源相互矛盾时并列并说明取舍理由
4. **产出 gap 清单**：调研得到的机制 vs 当前实现，逐项列出"已对齐 / 有差距 / 未实现"，
   含本卡范围外的项（半砖、游泳、梯子等）——这些会由 PM 登记为后续卡。
5. 若本机无网络：在报告中明确说明，退化为只读 `docs/research/01`，并在 gap 清单中标注
   "未获外部来源"，**不得凭记忆编造数值**。

## 接口契约（冻结项）

- 命名空间不变：`opencraft::physics`、`opencraft::client`。
- `step_player(PlayerState&, const InputState&, const IBlockSource&, const PhysicsConfig&)`
  **签名不变**；新机制通过 `InputState` 字段与 `PhysicsConfig` 常数表达。
- `PhysicsConfig`：新增常数**必须带单位注释与来源标注**（沿用现有风格：
  `// ⚖ docs/01 §2: ...` 或 `// <来源 URL> (访问 YYYY-MM-DD)`）。
- `InputState`：新增字段须给出默认值，保证既有调用方零改动可编译。
- 疾跑状态（是否在疾跑、双击计时）须为**可在无头测试中断言的显式状态**，
  不得只存在于客户端输入层——否则无法用物理回放测试锁定。

## 数值/规格依据（⚖ 为硬指标）

- `docs/01-gameplay-spec.md` §2：行走 4.317 / 疾跑 5.612 / 潜行 1.295 m/s；
  **疾跑跳均速 7.127 m/s**；跳跃初速 0.42 格/tick、跳高 1.2522 格；
  重力 0.08/tick²、阻尼 ×0.98/tick、终端 ≈78 m/s；体形 0.6×1.8 / 0.6×1.5。
- 手感项（§2 末）：疾跑 FOV 拉伸、潜行边缘防坠落。
- `docs/research/01` §1.1：疾跑需饥饿 > 6；**疾跑约有 0.6 秒启动判定（双击 W 或按 Ctrl）**；
  疾跑 FOV 默认约 +10%、随速度平滑过渡；疾跑时对生物撞击产生额外击退；
  单次疾跑跳水平最远约 4 格（常态跳跃约 2 格）。
  ⚠️ 上述"约"值须由你的调研给出更精确的数值或确认范围。

## 已知风险与提示

- **黄金回放是本卡最大的坑**：T007 的黄金文件锁死了物理数值，你的改动必然让它失配。
  先读 `tests/test_physics_golden.cpp` 的生成方式，再动手改物理。
- **空中模型的修法**（T007 报告的经验）：不要把 `air_drag` 直接绑到目标速度上——
  T007 的第一版试过"锚定目标速度 × (1−0.98) × 0.5"，导致连续跳跃掉速到步行的 40%
  后废弃。正确的做法是**先调研 MC 的实际空中规则**（是否给跳跃额外的水平冲量、
  空中加速度与地面比例），再照调研结果实现，不要凭直觉调参。
- 疾跑状态若放进客户端输入层会无法测试；请把它作为显式状态暴露给物理层（见「接口契约」）。
- FOV 属渲染表现项，不进物理状态；但"何时进入/退出疾跑"是物理项，两者要分清。
- 饥饿系统在 M2 才完整（当前 T007 只有字段）；饥饿门槛本卡只做"可配置常数 + 测试注入"，
  不要顺手实现整个饥饿模型。
- 不要引入新第三方依赖。
- 规格数值若与调研结论冲突：**以调研证据为准提出，由 PM 裁决**（数值即规格，规格只能由 PM 改）。
