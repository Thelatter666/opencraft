## 他提的两处待拍板 —— 全部裁决

### (a) 额外建了 `assets/items/` —— **不算越界，认可；卡面冻结布局予以更新**

他担心：卡面 §3.1 的冻结布局只列了 `blocks/`，他多建了 `items/`。

**裁决：认可，不构成越界。** 依据：
1. 卡面 §1 目标原文写「**为物品图标留出同类通道**」——通道的目录就是它的一部分；
2. 白名单写的是 `assets/**`（不是 `assets/blocks/` 一个子目录）。

⇒ **当场落实**：把 `items/` 补进卡面 §3.1 的冻结布局，消除"冻结布局与实际不一致"的漂移。

### (b) `resolve_assets_root()` 候选顺序 —— **认可**

```
$OPENCRAFT_ASSETS_DIR  →  <cwd>/assets  →  <cwd>/../assets
```

**裁决：认可。** 理由：
1. 环境变量覆盖在前，给了验收与 CI 一个确定性开关（PM 自己正是靠布局而非环境变
   量做 A/B 的，两条路都走得通）；
2. `<cwd>/../assets` 是被**既成事实**逼出来的——实际启动方式是 `cd build && ./opencraft`，
   而 build 在仓库根下 ⇒ `../assets` 正是仓库的 `assets/`。这不是 hack，是对现实的适配；
3. 每次启动**日志写明选中的路径**（`atlas: no assets/ tree found` /
   `atlas: 1/63 block tiles loaded from assets/blocks`）——**路径歧义被显式化**，
   这正是此类"自动探测"最容易埋雷的地方，他做对了。

⚠ 仅一条要求：**"选中了哪个根"必须始终出现在启动日志里**（现已满足），
因为"加载了 0 个"与"找错了目录"在画面上不可区分。

## 他自行决定的实现判断 —— 复核结论

| 判断 | PM 复核 |
|---|---|
| 自校验 PNG 签名（只认 PNG，改扩展名无效） | **认可**。比"只看扩展名"严，且拒绝得干净 |

| 新增静态库 `opencraft_client_assets` 使 client 与 tests 链接同一份 `atlas.cpp` | **认可**。避免"测试测的是另一份代码"（这正是 PM 的 A/B 装置想排除的风险，他从设计上就堵住了） |
| stb 只在 `asset_atlas.cpp` 定义实现宏 + `STBI_ONLY_PNG`/`NO_STDIO` + SYSTEM 引入 | **认可**。单 TU 实现宏是多 TU 重复符号的标准解法；缩到只解 PNG 也减小了面 |
