## 2. 架构：只解耦 Y

```
physics: step_player()  ──零改动──▶  tick 状态（50 ms 固定步长）
                                          │
                              prev_state / curr_state
                                          │
                    cam_pos = lerp(prev, curr, alpha)      ← partial-tick LERP
                                          │
                 ┌────────────────────────┴────────────────────────┐
                 ▼                                                 ▼
         X / Z：逐位直通                                  Y：临界阻尼弹簧
         （结构性保证，无滤波、无滞后）                    （ζ=1.0，ω=26）
```

**X/Z 为什么不能进弹簧**：水平方向加二阶滤波会把鼠标与平移输入变成**滞后**，
手感立刻变糟；research/09 §5.1 描述的也只是**垂直**解耦。`CameraFilter` 里
X/Z 是**赋值**而非滤波，所以「无水平滞后」是结构保证，不是调参结果——
单测直接断言 `f.x() == px` 位相等。

## 3. ⚠ 卡面建议的积分器不可用（实测推翻）

卡面 §实现要点 3 建议「半隐式欧拉」。**实测该积分器在本客户端的帧率下不稳定**：

```
ω = 26 rad/s, dt = 1/30 s  →  ω·dt = 0.867   落在稳定域外
  阶跃响应：单调=否，过冲 = +8446 格，终值发散到 -9562 格
对比 ω·dt = 0.433（60 fps）/ 0.181（144 fps）：数值上恰好没炸
```

即：**同一份代码在 60/144 fps 正常、在 30 fps 发散**——正是卡面自己禁止的
「帧率不一致」，而且更糟。临界阻尼二阶系统有闭式解，故改用**解析解**：

```
x = y - r,   x'' + 2ωx' + ω²x = -2ωm        （m = 目标斜率）
particular   x_p = -2m/ω
homogeneous  (A + Bt)e^{-ωt}
```

| 方案 | 30 fps | 8 fps | 任意 dt |
|---|---|---|---|
| 半隐式欧拉（卡面建议） | **发散（过冲 8446）** | 发散 | 有稳定上限 |
| 解析解（本卡采用） | 单调、无过冲 | 单调、无过冲 | 无上限 |

代价是每帧 1 次 `exp()`，相对一帧渲染不可测。

### 3.1 目标采样：按 tick 拐点分段

客户端的渲染目标是 partial-tick LERP，它是**分段线性**且拐点落在 tick 边界。
单帧跨过 tick 时用一个「弦」近似会在**拐点处引入帧率相关误差**（实测 30 fps
下 ~7e-3 格，而拐点分段可压到 ~1e-16）。故 `CameraFilter::update` 接受
`(mid_eye_y, mid_dt)`，把该帧拆成两段各自精确积分。`main.cpp` 在
`tick_clock.advance()` 之前捕获「tick 落地处的眼高目标」与拐点时刻。

### 3.2 参数标定（全部实测，非拍脑袋）

**ω = 26 rad/s**（0.6 格抬升的 95% 过渡时长）：

| ω | 纯阶跃 95% | 经 50 ms tick ramp 实测（30 fps） | 判定 |
|---|---|---|---|
| 22 | 0.216 s | **0.267 s** | 慢缘，发飘 |
| 24 | 0.198 s | 0.233 s | 可用 |
| **26** | **0.182 s** | **0.233 s** | **取此值**（窗口居中，两侧有余量） |
| 28 | 0.169 s | 0.200 s | 可用 |
| 30 | 0.158 s | 0.200 s | 快缘，余量薄 |

实测 30/60/144 fps 下 rise95 = 0.233 / 0.217 / 0.214 s，全部落在 **0.15–0.25 s**。

**滞后限幅 = 0.9 格**（两侧约束，非单侧）：

```
下界：0.6 格抬升的无约束最大滞后 = 0.567 格（60 fps 实测）
      ⇒ 限幅必须明显高于它，否则会咬合在台阶上，把 S 曲线压成
        「恒定偏移的线性跟随」——恰好毁掉本卡要的效果
上界：目标 = 眼高（站 1.62 / 潜行 1.27），相机最低在脚上方 (眼高 − 限幅)
      ⇒ 限幅必须 < 1.27，否则相机陷入地面
取 0.9：距台阶滞后 0.33、距潜行眼高 0.37，两侧都有余量
```

> **过程交代**：初版我取 0.6（= T-D8 步高），看似「台阶恰好装得下」。实测发现
> 无约束滞后已达 **0.567**，只剩 0.03 余量——限幅几乎必然咬合。改为 0.9。
> 这条是**实测发现的，不是设计出来的**，若按初值交付，台阶上的平滑会被限幅吃掉。

**瞬接阈值 = 20 格**：一个被 dt 钳制的帧内目标最多移动
`kCameraSpringMaxDt × 3.92 b/tick × 20 = 0.784` 格，快速下落每帧约 1.3 格。
20 格 ≈ 25 倍余量，同时远低于任何真实重生/读档/传送（数百格）。
> 初版取 2.0 格是**错的**：普通快速下落会被误判成传送并瞬接（反而丢掉平滑）。
> 已按物理上界重推，并在单测里加了「快速下落不得误判」的守门用例。

**dt 钳制 = 0.1 s**：解析解本身无稳定性问题，故这是**策略**上限（卡顿后单帧
最多移动多少），不是稳定性修复。

## 5. `main.cpp` 接入（最小改动）

**接入点**：`main.cpp:1099-1119`（原 `cam_pos` / `eye` 计算处）

```cpp
const glm::dvec3 cam_pos = prev_state.position + (curr_state.position - prev_state.position) * alpha;
const double eye_height = curr_state.pose == phy::Pose::Sneaking ? kEyeSneaking : kEyeStanding;
const double frame_dt = std::max(0.0, now - camera_last_time);   // 真实帧时长
camera_last_time = now;
if (!paused && ticks_this_frame > 0 && tick_kink_dt > 0.0 && tick_kink_dt < frame_dt) {
    camera.update(cam_pos.x, cam_pos.y, cam_pos.z, eye_height, frame_dt, tick_kink_eye_y, tick_kink_dt);
} else {
    camera.update(cam_pos.x, cam_pos.y, cam_pos.z, eye_height, frame_dt);
}
const glm::dvec3 eye(camera.x(), camera.y(), camera.z());
```

四个要点：
1. **帧率无关**：用 `now - camera_last_time`（主循环已有 `now`），**不用固定步长**。
2. **暂停**：`paused` 帧不传陈旧 kink（暂停时无 tick，`alpha` 不推进）；同时
   `frame_dt` 会被钳到 0.1 s，不会因长暂停而弹射。
3. **启动预置**：建 `CameraFilter` 时用物理起始位置 `reset()`，首帧无瞬态。
4. **重置**：卡面点名的三种情形——启动/读档（构造时 `reset`）、暂停恢复
   （`tick_clock.reset()` 后无 tick ⇒ 目标不变，弹簧自然静止）、**传送**
   （位移 > 20 格自动瞬接，无需在每个调用点手写重置，也就不会漏）。见 §8 建议表 S-3。

**结论**：T-D8 在物理层实现正确（单测 19 例、速度零损失均成立），但**在现行
客户端里没有触发入口**——因为世界里根本不存在 ≤0.6 的高差。这与 T-D8 报告 §1
已经预警的「纯整方块世界里本机制永远不触发」是同一件事，只是那次是**测试可表达
性**问题，这次是**实机可达性**问题：**用户抱怨的「上台阶瞬移」在 T-D8/T-D13 的
基线构建里不可能发生**。

**对用户原话的诚实解读**：用户说「上台阶像是瞬移上去」**且**「MC 有跳跃动作」。
后半句已由 PM 判定为 Auto-Jump（T-D14）。前半句若确为「瞬移」，则**在当前构建
里找不到对应机制**——玩家撞 1.0 坎会被**挡住**（`x=9.700`，水平速度归零），而不是
被抬上去。可能的其他来源（均未被本卡证实）：
- 跳跃落地时 `move_axis_y` 的落地夹持（每 tick 位移级，非整格）；
- 用户描述的是**期望**（希望走上台阶），而非已发生的瞬移。

**本卡的实际价值（不含糊）**：弹簧把**所有可达的垂直突变**都消除了——姿态切换
0.35 格（实机实测 0.35 → 0.000063，§6.1）、落地、跳跃弧线。即：**架构正确、
可达场景全部生效**；但「上台阶」这一句要等**内容侧接缝**（`WorldSource` 接
`shape_top_at`，随 M2 半砖/地毯内容卡）之后才能实机复现与复验。

**建议**（交 PM 裁决，本卡未自行改任何规格）见 §8 的 S-1/S-2。
